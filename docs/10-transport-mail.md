# 10 · 邮件传输

> 数据来源：`research/email.md`（2026-10-23 采集，逐条带 URL）。本文只放结论与设计，不复述取证过程。
> 一句话结论：**额度不是问题，多邮箱是错的解法，自有域名 + 一个发信地址 + 每会话一个 Reply-To 才对。**

---

## 1. 五个结论

| # | 问题 | 结论 |
|---|---|---|
| 1 | 邮件发送上限会成为瓶颈吗 | **不会**。个人助理一天 20–80 封，免费档普遍在 100–500/天 |
| 2 | 注册多个邮箱轮换发信能解决吗 | **不能，且有害**。见 §3 |
| 3 | 那额度紧张时怎么办 | **聚合 + 优先级 + 额度账本**，不是加地址。见 §4 |
| 4 | 会话怎么绑定 | **自有域 catch-all，`Reply-To: s-<id>@domain`**。见 §5 |
| 5 | 怎么无缝换服务商 | **逻辑地址与后端账号解耦**，换的是后端，不是地址。见 §9 |

## 2. 额度实况

| 服务 | 每日额度 | 单封收件人 | 超限后果 |
|---|---|---|---|
| Gmail 个人 | 500 封/天 | 500 | 禁发 1–24h，**仍可收信**，不封号 |
| Google Workspace | 2,000 封/天 | 500（总收件人 10,000/天） | 同上 |
| Outlook.com | 5,000 收件人/天（其中"无历史关系"1,000/天） | 500 | 退信/限流 |
| M365 / Exchange Online | 10,000 收件人/天 | 500 | 同上 |
| QQ 个人 | **不公布**（"保密数据"），按发信 IP + 发件人域双维度阶梯限流 | — | `550 Connection frequency limited` |
| 阿里云 DirectMail | 2,000 封/天（初始），免费共 2,000 封且每日最多 200 封 | 100 | 退信 |
| Resend 免费 | 100 封/天 | — | 限流 |
| Postmark 免费 | **100 封/月**（不是每天） | — | — |

**两个容易踩的坑**：

1. **计量口径不同**：Gmail 计"封"，Microsoft 计"收件人"。如果你一封发给 5 个人，在 Microsoft 那边算 5。
2. **滚动窗口**：Gmail 是滚动 24h，不是自然日零点重置。"今天用完了"可能是昨晚的额度还没滚出去。

**换算到 Mephisto**：一天典型用量 = 用户对话回信 10–30 + 聊天摘要 3–8 + 提醒 2–10 + 系统告警 <2，合计 **20–50 封**。即便全走 Gmail 个人档（500），也只用了 10%。**额度不是设计约束。**

真正要防的是**突发**：一个 500 人群的防抖参数配错，一晚上能产出上百封摘要。所以 §4 的账本是防"自己把自己打爆"，不是防服务商。

## 3. 为什么多邮箱池化是错的

四个独立的理由，任何一个都足以否决：

### 3.1 服务商按域和 IP 限流，不按邮箱

QQ 官方文档写得很明确：限流对象是"**发信 IP 或发件人根域名**"，且"仅更换其中一个对象无法规避限制"。也就是说，同一个域下的 10 个邮箱共用一套限额——**多注册邮箱在同一个域下不产生任何额度**。

跨域注册（gmail + outlook + qq 各一个）能绕开单域限额，但代价是下一条。

### 3.2 DMARC 对齐逼你用自有域

现代收件方要求 `From:` 域与 SPF/DKIM 签名的域**对齐**。你没法"用 Gmail 的服务器发一封 From 是 example.com 的信"——除非你在 example.com 配了 SPF/DKIM 并授权 Gmail 代发。一旦你这么做了，你的信誉就集中在自有域上，**多邮箱不再分摊任何东西**。

### 3.3 新域要预热 2–4 周

新注册的域名发信，收件方默认不信任。第一天就发 100 封，大概率直接进垃圾箱或触发限流。预热是"每天递增一点"，这让"池化"在最需要它的场景（突发量）完全失效——新域根本不敢发。

### 3.4 多 From 触发钓鱼观感，且回复归集崩溃

同一件事的邮件从 `a@x.com`、`b@y.com`、`c@z.com` 轮着发，收件人（包括你自己）看到的是一堆互不相关的发件人，线程也聚合不到一起。**这直接破坏 §7 的线程稳定性**——而线程稳定是会话管理的地基。

**结论：放弃池化。** 唯一可接受的多地址形态是「**同域 catch-all 多地址收信 + 单一地址发信**」（见 §5）。

## 4. 那突发怎么兜

三道闸门，全部在 `mail-send` 里，Agent 无法绕过：

### 4.1 额度账本（防自己打爆）

```sql
CREATE TABLE quota_ledger (
  lane     TEXT NOT NULL,      -- 'reply' | 'notify' | 'system'
  day      TEXT NOT NULL,      -- '2026-10-26'（本地日）
  sent     INTEGER NOT NULL DEFAULT 0,
  cap      INTEGER NOT NULL,
  PRIMARY KEY (lane, day)
);
-- 发送前：UPDATE ... SET sent=sent+1 WHERE sent < cap RETURNING sent;
-- 返回 0 行 = 今日满，转排队
```

**原子自增 + 条件更新**，不是"查了再发"。多线程也不会超。

### 4.2 优先级与降级

| lane | 上限（建议） | 满了怎么办 |
|---|---|---|
| `reply`（用户对话的回信） | 80/天 | **永不降级**，超了说明系统出问题 |
| `notify`（摘要、提醒、告警） | 60/天 | 合并进下一条；同一天内多次摘要合并成一封 |
| `system`（失败通知、心跳） | 10/天 | 丢弃重复，只留最后一条 |

`reply` 与 `notify` **分 lane 记账但用同一个 From**：这样突发摘要吃不到对话的额度，同时不引入多 From 的问题。

### 4.3 过期即作废

摘要邮件带 `expires_at`（默认 6 小时）。**过了就永远不发**——早上十点收到昨天晚上十点的群聊摘要没有价值，只会消耗注意力和额度。发送器遇到过期直接移 `sent/` 并标 `expired`。

## 5. 地址体系

### 5.1 三层地址

| 层 | 例子 | 谁看得见 | 变化频率 |
|---|---|---|---|
| **逻辑地址** | `m@mephisto.example.com`、`s-7f3a2c@…` | 用户、通讯录 | 永不（换服务商也不变） |
| **后端账号** | `mephisto@qq.com`、`agent@resend.dev` | 只有配置 | 可换 |
| **传输凭据** | SMTP/IMAP 密码、API key | 只有 `.secrets/` | 可换 |

**这三层分开，就是"无缝切换"的全部。** 换服务商 = 改第 2、3 层，第 1 层不动，用户的通讯录与所有历史线程继续有效。

### 5.2 From 固定，Reply-To 随会话

```
From:     Mephisto <m@mephisto.example.com>        ← 永远不变
Reply-To: <s-7f3a2c@mephisto.example.com>          ← 每条会话一个
To:       用户
```

这是本设计里最关键的一处：

- **From 恒定** → 收件方信誉集中、用户永远知道"这是同一个人"、白名单一次就够。
- **Reply-To 每会话一个** → 用户点"回复"时，客户端自动把收件人填成会话地址。**零输入就完成了 K2 绑定**（见 `20-sessions.md` §4）。
- 两者叠加 = 线程有**两个独立证据**（References 链 + 地址），任一个坏掉还能路由。

### 5.3 为什么用 `Reply-To` 而不是 `+tag` 或 `From`

| 方案 | 可行性 |
|---|---|
| `From: user+tag@domain` | ❌ 子地址在多数服务商**不能作为发件人**；Exchange 明确不支持 |
| `To: user+tag@domain` | ⚠️ Gmail 可靠，Exchange 默认开启但管理员可关，**QQ/163 大概率 550** |
| `Reply-To: s-<id>@domain` | ✅ 任何客户端都保留；自有域 catch-all 必然收得到；不依赖服务商是否剥离 `+tag` |

**所以会话主键用 `Reply-To` 的完整子域地址，不用 `+tag`。** 这条是研究的明确建议，也避免了"某家把 `+tag` 规范化掉"这个不可控变量。

### 5.4 需要的 DNS

```
MX      example.com           → <邮件服务商>
TXT     example.com           "v=spf1 include:<provider> -all"
TXT     _dmarc.example.com    "v=DMARC1; p=quarantine; rua=mailto:dmarc@example.com"
TXT     <sel>._domainkey      <provider 给的 DKIM 公钥>
```

`p=quarantine` 起步，跑顺了再 `p=reject`。**先有 DMARC 报告地址**，否则出了问题你连"为什么进垃圾箱"都看不到。

## 6. 收信：四种方案

| 方案 | 成本 | catch-all | 延迟 | 复杂度 | 评价 |
|---|---|---|---|---|---|
| **A. 自有域 → 转发到真实邮箱 → IMAP 轮询** | 域名费 | ✅ | 30–60s | 低 | **v1 推荐** |
| B. Cloudflare Email Routing → Worker → HTTP/R2 | 免费 | ✅ | 秒级 | 中 | 好，但 Worker 逻辑要自己写 |
| C. Gmail API push（Pub/Sub） | 免费 | ❌ 无自有域 | 秒级 | 高 | OAuth 审核 + 7 天续订 |
| D. 自建 MX（maddy / docker-mailserver） | VPS | ✅ | 秒级 | **很高** | 只收可以，发信必进垃圾箱（IP 无信誉） |

**v1 走 A**：Cloudflare Email Routing 免费把 `*@example.com` 转发到你的 Gmail/QQ 邮箱，Mephisto 用 IMAP 读那个邮箱。好处：

- 零额外服务、零公网暴露（家里的机器不需要开端口）；
- catch-all 免费，`s-*@` 地址立刻可用；
- 转发时 `To:` / `Delivered-To:` 保留原地址，路由 K2 照常工作；
- 换服务商只改转发规则。

代价：延迟 30–60s（可接受，邮件本来就是异步的）；IMAP 要处理断线重连。

**发信**不能走这个转发（转发是收信）。发信走"自有域授权的 SMTP"，两条常见路径：

1. **邮箱服务的"自定义域名/发信别名"**（如 Gmail 的 "Send mail as" 绑定自有域 SMTP）——便宜，但配置繁琐；
2. **事务邮件服务**（Resend / 阿里云 DirectMail / Cloudflare Send）——配置干净，免费档够用，但要注意他们可能加退订页脚（对事务邮件可关）。

> ⚠️ 不要把 `From` 设成自有域却用别家的默认发信域投递——DMARC 对齐会失败，结果就是进垃圾箱。

## 7. 线程：五条硬结论

这五条是从真实踩坑里总结的，全部要实现，不是建议：

1. **Message-ID 自己生成**：`<uuidv4@yourdomain>`，写库唯一索引。**绝不交给 SMTP 客户端生成**——它可能复用/碰撞，撞了就被收件方当重复消息丢掉。
2. **`In-Reply-To` 只放父消息的 Message-ID（单个），`References` 放全链且升序**。两个都要写：Outlook 桌面版只认 `In-Reply-To`，Gmail 更依赖 `References`。
3. **主题只在首封决定，之后逐字继承 `Re: <原主题>`**。不加 `[tag]`，不本地化成 `回复:`——部分客户端会因此重算会话。
4. **References 必须主动截断**：保留首项 + 最近 ~20 项。Cloudflare 对 >100 条直接拒收，Exchange 单头 >32KB 报 552。**不截断的线程跑到 200 封就会开始丢信。**
5. **线程的真相在地址**：`Reply-To` 的会话地址是主键，头部链只做交叉校验。

### 7.1 客户端差异（必须知道的坑）

| 客户端 | 聚合依据 | 后果 |
|---|---|---|
| Gmail / Apple Mail | 头部为主 | 正常 |
| Outlook 桌面 | **`Thread-Index`，不读 References** | 跨端看同一线程会不一致 |
| Outlook 网页 | 头 + 主题 | 主题被改就断 |

所以：**不要指望"所有客户端看起来都像一个会话"。** 我们自己的状态（`session_alias`）不依赖任何客户端怎么显示。

## 8. 附件

| 限制 | 数值 |
|---|---|
| Gmail | 25 MB |
| Outlook.com | 25 MB（OneDrive 链接 2 GB） |
| M365 发送 / 接收 | 35 MB / 36 MB（OWA 112 MB） |
| 阿里云 | 整封 ≤15 MB，官方建议按 **8 MB** 准备 |
| Base64 膨胀 | **+33%**（官方口径 1.5 倍以上） |

**设计取值：单封总附件 ≤7 MB。** 超过 5 MB 时改为"上传到对象存储 + 签名 URL（7 天有效）+ 邮件里放链接"。

另外一条容易被忽略的：**Agent 回信不要回带附件**。用户发来 20 MB 的表格，Agent 回信时如果把原文件再带回去，等于双倍占用且毫无意义。只在明确需要交付产物时带。

## 9. 无缝切换：具体怎么做

### 9.1 能力矩阵（适配器只声明它支持的）

```python
class MailBackend(Protocol):
    name: str
    caps: set[str]          # {'send','poll','idle','flags','move','labels','quota'}
    def send(self, env: Outbound) -> str: ...
    def fetch(self, cursor: Cursor) -> tuple[list[Inbound], Cursor]: ...
```

| 后端 | 用在哪 |
|---|---|
| `imap_smtp` | v1 默认。任何支持 IMAP/SMTP 的邮箱 |
| `jmap` | 将来（Fastmail 等），原生支持 push |
| `gmail_api` / `graph` | 需要 webhook 级延迟时 |
| `http` | **自建信道**（同一个 `Envelope`，不走邮件协议） |

### 9.2 切换的步骤（目标是"改配置，不改代码"）

1. 在新的服务商配好收信（catch-all 或转发）与发信域；
2. 在 `config.toml` 改 `mail.backend` 与对应凭据；
3. **DNS 不动**（MX 与 From 域仍是你的域）；
4. `mephisto doctor` 自检；`mephisto mail test` 发一封测试信到自己的会话地址；
5. 旧后端保留 7 天只收不发，然后下线。

用户侧要做的事：**零**。通讯录里的地址没变，历史线程没断。

### 9.3 什么会破坏可切换性

| 反模式 | 后果 |
|---|---|
| 把邮箱地址写进代码/模板 | 换服务商要改代码 |
| 依赖服务商特有的标签/文件夹语义 | 换后端就丢状态 |
| 用 Gmail 的 `X-GM-*` 扩展做线程 | 绑死 |
| 把 `Message-ID` 交给服务商生成 | 换后端后线程全断 |
| 用 `+tag` 做会话主键 | 换到不支持子地址的服务商就废 |

## 10. 鉴权与防伪造

邮件是最容易被伪造的信道。五层：

1. **发件人白名单**：只有配置里的地址（用户自己的几个邮箱）能创建/操作会话。`From` 不在白名单 → 直接丢弃并记日志，**不回信**（回信等于告诉对方地址有效）。
2. **看 `Authentication-Results`**：Gmail/Outlook 会在头里写 SPF/DKIM/DMARC 结论。解析它，`dmarc=fail` 的一律降级为"只读、不执行"。
3. **不用 `From` 显示名做判断**：显示名可以随便填。
4. **敏感操作二次确认**：删除、对外发信、改配置，要求回信里带一个短码（由 Agent 在上一封里给出）。
5. **不回自动回复**：`Auto-Submitted` / `Precedence: bulk` / `List-Id` 存在的信，一律不触发 Agent 运行。
