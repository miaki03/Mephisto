# 40 · 聊天记录整理（微信 / QQ）

> 你给了三种触发方案。本文的结论是第四种：**采集与总结彻底解耦，采集常开、总结防抖、投递聚合**。

---

## 1. 来源与现状：技术来自 WeFlow，运行时已经自持

先把来源说清楚，这关系到后面所有的判断：

- **技术来源是 WeFlow**。`wxread` 不是另起炉灶，是把 WeFlow 里有价值的那部分（取密钥、SQLCipher 页解密、分片枚举、内容解码）**提取出来自己持有**。原作者与项目的贡献不该被抹掉，所以这里仍然写"来源于 WeFlow"。
- **变的是运行时依赖，不是技术血缘**。WeFlow 这个**应用**不能再当运行时用；`wxread` 这个**实现**可以。

上一轮把 WeFlow 拆到二进制层（`refs/chatlog/`），三条对设计有硬约束的结论：

| 事实 | 出处 | 对 Mephisto 的含义 |
|---|---|---|
| 应用授权里**写死了截止日期 `2026-10-16 00:00`**，过期即 `-101`，且远端可吊销 | `50-weflow-expiry.md` §4.2 | **这个应用已经停摆**。把产品建在它上面，等于建在一个已过期的组件上 |
| 内置 Agent 把聊天正文发到 `api.deepseek.com`，原生组件还有遥测上报 | `90-risks.md` A3 | 不能用它的摘要功能；摘要必须在自己这一侧做 |
| 反撤回功能会**改写微信数据库**（建表 + 触发器） | `90-risks.md` A4 / `20-weflow-datamodel.md` §6 | 与"只读"前提冲突，必须显式排除 |

**所以：能力照旧，换实现。** 主路径是 `wxread`（`[确认-实测]` 能读真实群消息）。它与 WeFlow 的唯一耦合是 passphrase 存在 WeFlow 的配置文件里（DPAPI 保护）——只要那个文件在，应用是否过期、是否卸载都无关（`refs/wxread/README.md` §6）。

WeFlow 剩下的价值有两个：**passphrase 丢了之后重新取一次**；以及作为"微信改版后参数变了"的参照。它不是运行时依赖，但它是**技术来源**。

> 归因建议：在 `wxread` 与 Mephisto 的 README 里各留一行——"读取链路的技术来源是 WeFlow（hicccc77/WeFlow），本项目只提取其数据层实现并自持，不再依赖其运行时分发"。这既是事实，也省掉将来被问"这是不是抄的"的麻烦。

## 2. 一条更重要的原则：能不能重算

把整条链路拆成四段，看每段的"可重算性"：

| 段 | 做什么 | 能重算吗 | 所以 |
|---|---|---|---|
| **采集** | 解库、解码、落 `chatlog.sqlite3` | **不能**。微信分片会滚动、QQ 官方 Bot 没有历史接口、NapCat 离线即永久空洞 | **必须最可靠，宁慢勿丢** |
| **清洗** | 去噪、合并连发、识别接龙 | 能（从库里重跑） | 可以随时改规则、回填 |
| **总结** | 调模型出结构化摘要 | 能（但要花钱） | 可以重来、可以换模型 |
| **投递** | 拼邮件、发出去 | 不能（发出去了） | 要幂等、要留档 |

**设计推论：采集进程的可用性优先级高于一切。** 它挂了，丢的是永远补不回来的东西；总结挂了，明天重跑就行。

这也是对你三种方案的统一回答：**方案一和方案二不是二选一，它们共用同一个 `digest` 实现，只是触发器不同。**

## 3. 触发策略对比

| 方案 | 延迟 | 噪声 | 成本 | 致命问题 |
|---|---|---|---|---|
| 一 · 用户手动发信触发 | 取决于用户 | 无 | 低 | 用户想不起来；"重要消息"往往正是他没想到要问的 |
| 二 · 每条新消息触发 | 最低 | **极高** | **极高** | 一个 500 人群一天能耗掉几百次调用；接龙一条能触发几十次 |
| 三 · 定时批量（如每天 22:00） | 最长 24h | 低 | 低 | 紧急消息（"明早交表"）当天看不到 |
| **四 · 事件 + 防抖 + 聚合投递（推荐）** | 1–20 分钟 | 低 | 中 | 需要调参数；见 §4 |

方案四 = 方案二 + 三个闸门：

1. **防抖（debounce）**：不是"有新消息就跑"，是"**安静下来之后**才跑"。
2. **白名单**：只监听 `watch` 表里的会话，不是全部。
3. **聚合投递**：一小时内多个会话的结果合并成一封邮件，不是每个会话一封。

## 4. 防抖的具体算法

### 4.1 每个会话一个状态机

```
IDLE ──新消息──> PENDING(记录 first_ts, last_ts, count)
PENDING ──又有新消息──> PENDING(更新 last_ts, count++)
PENDING ──满足任一 flush 条件──> FLUSHING ──> 写 chat_digest ──> IDLE
```

### 4.2 flush 条件（四选一）

| 条件 | 参数 | 作用 |
|---|---|---|
| 静默够久 | `now - last_ts ≥ 120s` 且 `count ≥ 1` | 主路径：人聊完一段了 |
| 攒得太久 | `now - first_ts ≥ 20min` 且 `count ≥ 5` | 防止一个热闹的群永远不静默 |
| 命中高优先 | 消息 `@我` / 命中 `watch.keywords` / 来自 `watch.vip` | 立即 flush，走"紧急通道" |
| 量太大 | `count ≥ 60` | 防止一次喂给模型太多；先切一半 |

### 4.3 静默时段

`23:00–07:30` 不投递（不打扰），但**继续采集与总结**，攒到 07:30 一封"夜间汇总"。

### 4.4 风暴保护

单个会话 `> 200 条/小时`：降级为"每 30 分钟一次"，且摘要只输出"话题 + 决策 + 要找你的"，不做逐条解读。

### 4.5 为什么是 120 秒

人在微信群里连续发消息的间隔通常在 5–30 秒。120 秒能覆盖"一段话分四五条发"的情况，又不至于让正常的对话延迟到不可接受。这个数要按真实使用调，先按 120s 起步。

### 4.6 冷却与迟到消息（2026-10-25 补充）

**问题**：消息不一定一次全到。微信是先写本地库、我们再轮询；同一个人可能隔几秒发一条，也可能隔几十秒。如果只按「静默 120 秒」一个条件，就会出现：第 120 秒发了摘要，第 130 秒又来两条 → 立刻再触发一次 → **反复提醒**。

**三层闸门，缺一不可**：

| 闸门 | 规则 | 作用 |
|---|---|---|
| 静默判定用**消息时间戳** | 用 `sort_seq`（= `create_time*1000+ms`）算 `last_ts`，不是「我发现它的时刻」 | 迟到的旧消息不会把静默"重置"成新一轮 |
| **冷却期** | 一次 flush 后该会话进入 `cooldown`（默认 10 分钟），期间新消息只累积不触发 | 挡住"刚发完又来两条" |
| **最小间隔** | 同一会话两次摘要间隔 ≥10 分钟；每小时 ≤3 次 | 兜底限流 |

**迟到消息归属**（这条最容易设计错）：

- 消息时间戳**落在已发摘要的时间窗口内** → 归入「补记」，**不单独发新摘要**；
- 补记累积到 ≥5 条，或命中 `@我`/关键词 → 才补发一条（并标明「补充」）；
- 每次都按 6 小时重叠窗口回看，靠 `chat_msg.uid` 唯一索引吃重复（§5.4）。

状态机因此变成三段：

```
IDLE ──新消息──> PENDING ──静默≥120s 且 now≥cooldown_until──> FLUSHING ──> COOLDOWN(10min) ──> IDLE
                     ↑                                                │
                     └──────────── cooldown 期间新消息只累积 ──────────┘
```

### 4.7 哪些会话要总结：不写死，自动发现

**原则：采集全量，摘要挑着来。** 两条理由：

- 采集**不可重算**（分片会滚动、Bot 无历史），所以不做取舍，全收；
- 摘要可重算、要花钱、会打扰，所以必须挑。

所以「监听列表」是一张表，不是一个配置数组：

```sql
CREATE TABLE watch (
  channel  TEXT,             -- wechat | qq
  conv_id  TEXT,
  name     TEXT,             -- 冗余存名字，改名历史也有据
  state    TEXT,             -- candidate | watched | muted
  source   TEXT,             -- auto | user
  keywords TEXT,             -- JSON 数组，命中走紧急通道
  created_at INTEGER, updated_at INTEGER,
  PRIMARY KEY (channel, conv_id)
);
```

**新会话怎么进表**：采集器发现没见过的 `conv_id` → 自动插入 `state='candidate', source='auto'`。**不写死任何群名，新群新好友第二天就会出现在表里。**

**从 candidate 变成 watched 的路子有两条**：

| 路子 | 规则 |
|---|---|
| 你手动开 | App 里一个开关，或对 agent 说「把 XX 群加入总结」 |
| 自动建议（仍要你点） | 7 天内 ≥30 条且 ≥3 人参与；或私聊里你回复过 ≥3 次；或命中已 watched 会话的同一批关键词 |

**每天一条「发现新会话」通知**（最多列 5 个，避免刷屏）：

```
发现 3 个新会话：
· XX班通知群   7 天 142 条 · 建议总结      [开启] [忽略]
· 张老师       7 天 6 条 · 私聊            [开启] [忽略]
```

`muted` 的会话仍采集、仍可手动摘要，只是**不自动发**。

### 4.8 策略层：你定规则，AI 只做脏活

三层，优先级从低到高：

| 层 | 存在哪 | 谁改 |
|---|---|---|
| 全局策略 | `config.toml` 的 `[watch.policy]` | 你改配置 / App 设置页 |
| 会话级 | `watch` 表一行 | App 里一个开关（**优先级更高**） |
| AI 建议 | `watch_decision` 表 | 只提建议；`source='user'` 的行**永不被覆盖** |

```toml
[watch.policy]
default         = "candidate"      # 新会话默认状态
auto_mute       = ["noise", "service"]
auto_watch      = []               # 默认不自动开启；想全自动就填 ["useful"]
quiet_hours     = "23:00-07:30"
min_messages_7d = 30               # 低于这个数不打扰你
urgent_keywords = ["@我", "截止", "交表", "报名"]
```

**AI 怎么判（省钱版，两步）**：

1. **先跑启发式**（不花钱）：群名含「广告/福利/优惠/砍价/红包/助力」、链接占比 >40%、红包/小程序消息占比高、200 人以上且从不 `@我`、7 天零消息 → 直接初判。
2. **只有拿不准的才调模型**：喂 20–30 条代表消息 + 会话名 + 统计（消息量/发言人数/链接比）。
3. 模型只输出四个字段：

```json
{"label": "noise", "confidence": 0.86, "reason": "全是拼多多砍价链接", "evidence": [1201, 1203]}
```

`label` ∈ `useful` / `noise` / `dormant` / `service`（公众号、机器人、系统通知）。

**自动动作**：

| AI 判定 | 置信度 | 动作 |
|---|---|---|
| `noise` | ≥0.8 | 自动 `muted`（采集照旧），**次日汇总里告知，可一键恢复** |
| `service` | ≥0.8 | 自动 `muted` |
| `dormant` | — | 什么都不做，30 天后再评 |
| `useful` | ≥0.9 且你有回复 | 进「建议开启」清单，**仍要你点一下** |

**四条硬约束**：

- **永不覆盖 `source='user'`**：你设过的，AI 不碰。
- **永不自动 `watched`**：摘要要花钱、会打扰，这一步必须你点头。
- **可审计**：每次判定写 `watch_decision`（含样本消息 uid），UI 里点「为什么」能看到那几条原文。
- **可复评**：消息量突增 3 倍 / 满 30 天 / 你手动改过标签 → 重评一次。

```sql
CREATE TABLE watch_decision (
  id INTEGER PRIMARY KEY,
  channel TEXT, conv_id TEXT, at INTEGER,
  prev_state TEXT, new_state TEXT,
  label TEXT, confidence REAL, reason TEXT,
  evidence_uids TEXT,      -- JSON：判据用的那几条消息
  actor TEXT               -- ai | rule | user
);
```

**你要的效果就是这条**：广告群不用你一个个设，它自己识别、自己静音，只在可能判断错的时候告诉你一句。

## 5. 清洗：在喂模型之前必须做的四件事

**清洗不是优化，是必需。** 不做的话，一个接龙能让模型输出四条一模一样的摘要。

### 5.1 连发合并

同一发送者在 `120s` 内的连续文本消息，合成一条（保留时间跨度）。这是最省 token 的一步。

### 5.2 噪声折叠

| `local_type` base | 处理 |
|---|---|
| 47 表情 / 3 图片 / 34 语音 / 43 视频 | 不出正文，只计数（`[图片×12]`） |
| 10000 系统提示（入群/撤回/拍一拍） | 只留"撤回"与"改名"，其余计数 |
| 49/33 小程序、49/2000 转账、红包 | 只留标题（appmsg 的 `<title>` 是可读的） |
| 公众号推送（`gh_*`） | 默认整条丢弃，除非在 `watch` 里 |

### 5.3 接龙折叠（你点名的问题）

接龙的特征很好识别，不需要模型：

```
命中条件（任一条，且窗口内连续 ≥3 条）：
  - 消息文本匹配 /^\s*\d+\s*[\.、．\)）]\s*\S/  （"1. 张三"）
  - 文本包含 "接龙" / "报名" / "统计一下" / "群收款"
  - 连续 ≥3 条消息形如 "+1" / "1" / "我"
```

命中后**不逐条喂模型**，而是抽成一条合成记录：

```json
{"kind": "relay", "title": "周六聚餐接龙", "count": 17,
 "new_entries": ["18. 王五"], "first_ts": "...", "last_ts": "..."}
```

投递规则：

- 接龙**进行中**：只在夜间汇总里提一句"周六聚餐接龙已 17 人"，不单独发邮件。
- 接龙**结束**（静默 30 分钟且不再增长）：输出一次完整名单。
- 只有"接龙里出现了你的名字"或"截止时间在 24h 内"时，才走紧急通道。

### 5.4 去重

`chat_msg.uid = (channel, conv_id, sort_seq)` 唯一索引。微信的 `sort_seq = create_time*1000+ms` 跨分片可比（`refs/wxread/core-facts.md` F3），`local_id` 不可用（有 47 处逆序）。

**每次拉取回看 6 小时重叠窗口**兜住迟到写入，靠唯一索引吃掉重复。这是最省心的幂等做法。

## 6. 摘要的产物结构

不要让它输出一段散文。**结构化，才能被后续查询和投递复用。**

```json
{
  "conv": {"id":"45365759247@chatroom","name":"XX班通知群","channel":"wechat"},
  "window": {"from":"2026-10-26T08:00:00+08:00","to":"2026-10-26T09:12:00+08:00"},
  "counts": {"total": 143, "text": 88, "image": 31, "relay": 1, "noise": 23},
  "topics": [{"title":"秋游报名","gist":"班委发起，10-28 截止","who":["班长"]}],
  "decisions": [{"what":"秋游改到 11-02","by":"班主任"}],
  "actions": [{"what":"交 50 元","owner":"我","due":"2026-10-28"}],
  "questions_for_me": ["张老师问你周三能不能到"],
  "relay": {"title":"秋游报名","count": 17, "closed": false},
  "open_loops": ["班费还没收齐"]
}
```

投递时再渲染成邮件正文（Markdown → 文本 + HTML）。**存储用 JSON，投递用渲染**——这样同一份摘要在邮件、App、网页里都能用。

## 7. 投递：把"聚合"做成硬规则

| 通道 | 频率上限 | 内容 |
|---|---|---|
| 紧急 | 每小时 ≤1 封 | `@我`、关键词、接龙点名、24h 内截止 |
| 常规 | 每小时 ≤1 封 | 多个会话的摘要合并在**一封**里 |
| 夜间汇总 | 每天 1 封 | 22:00 或 07:30，全部监听的会话 |

**"每小时 ≤1 封"不是建议，是发送层的硬闸门**（见 `10-transport-mail.md` 的额度账本）。聊天摘要永远不能把当天的额度吃光——额度要留给用户自己的对话回复。

## 8. skill 的形态

一个 CLI，四个子命令，输入输出都是 JSON。**手动触发和自动触发调的是同一个实现**：

```bash
mephisto chatlog sync                       # 采集（daemon 每 60s 调）
mephisto chatlog digest --conv <id> --since <ts> --until <ts>
mephisto chatlog digest --all --window 24h  # 夜间汇总
mephisto chatlog search "关键词" --conv <id> --limit 20
```

配套一个 `SKILL.md`（人/模型都能读）：什么时候该用、参数含义、返回结构、常见错误。**技能不是一个 prompt，是一个有稳定契约的命令。**

## 9. QQ 侧：走只读本地库，不碰账号协议

**你的约束改变了结论**：你没法把官方 Bot 拉进已有群，所以 Bot 路线出局。剩下的路线必须同时满足：能读全量、**不发消息**、不给账号带来风控风险。

| 路线 | 能读全量 | 要登录你的账号 | 有发送能力 | 结论 |
|---|---|---|---|---|
| 官方 Bot | ✅ | 否 | ✅ | ❌ 你无法把它拉进已有群 |
| NapCat / OneBot 11 | ✅ | **是** | ✅（要网关拦） | ❌ 封号风险 + 完整机器人框架 |
| **qqflow-server（只读解密本地库）** | ✅ | **否** | **否** | ✅ **采用** |
| QQFlow 桌面版 | ✅ | 否 | 否 | 备选：GUI 导出 TXT/CSV，不适合常开采集 |
| 自己写解密再读 | ✅ | 否 | 否 | 远期：qqflow-server 已经做了，没必要重写 |

### 9.1 qqflow-server 是什么（第三方，`[确认-文档]`，本机未跑）

[`ren-yc/qqflow-server`](https://github.com/ren-yc/qqflow-server)：**无头 HTTP API + SSE 服务**，读本地 QQ NT 的 `nt_msg.db`，默认 `127.0.0.1:5032`。

| 特性 | 内容 | 对我们的意义 |
|---|---|---|
| 解密 | SQLCipher 4（`kdf_iter=4000` / HMAC-SHA1 / PBKDF2-HMAC-SHA512 / AES-256-CBC），先剥 1024 字节自定义头 | 与 `nt_msg_db_util` 的字段研究一致 |
| 实时性 | **直读实时源库，QQ 运行中可读，无镜像** | 关键：不用关 QQ |
| 增量 | 全量扫描建内存索引 + 文件系统事件（notify）+ 慢速兜底轮询 | 近实时可达 |
| 密钥 | **不做提取**：你 POST 一个 16 字节 ASCII key，仅存内存、不落盘 | 密钥提取是唯一要自己解决的一步 |
| 鉴权 | token 存 OS 凭据库（`QQFLOW_TOKEN`） | 本机回环够用 |
| 接口 | sessions / messages / contacts / group members / media / SSE | 正好当我们的 `Source` 数据面 |
| 生态 | 有 Python SDK（`qqflow-sdk`）、有 stdio MCP 文档 | 接起来不费劲 |

### 9.2 密钥从哪来（唯一有风险的一步）

它明确**不做密钥提取**，要外部工具：`QQBackup/QQDecrypt`、`qq-win-db-key`，或 QQFlow 桌面版的「Windows Debug API 注入」。

| 项 | 事实 | 我们怎么做 |
|---|---|---|
| 原理 | 通过 Debug API 读 QQ 进程内存里的 16 字节 key | 一次性、手动 |
| 风险 | **可能触发杀软/EDR 报警** | 只在你手动执行时发生 |
| 频率 | 一般长期有效，QQ 大版本升级后可能要重取 | 一年几次 |
| 存哪 | `secrets/`（gitignore），重启后重新注册给 qqflow-server | 不进数据库、不进日志 |

**这是整条链上唯一「越界」的动作，且只发生一次、只读内存、不写 QQ 数据。** 和 NapCat「长期以你的身份登录并收发消息」是量级不同的风险。

### 9.3 我们怎么接（适配器，约 200 行）

```
qqflow-server (:5032) ──HTTP/SSE──► adapters/chatlog/qq.py
                                      │ 归一化成 11 个字段
                                      ▼
                                chatlog.sqlite3（我们自己的归档）
                                      │
                                      └─► 摘要流水线（与微信完全同一套）
```

**为什么还要落到自己的库**：`qqflow-server` 是第三方，会升级、会挂。我们的 `chatlog.sqlite3` 独立存在——它挂了能从源库重扫，我们挂了不影响它。这和 §2「能不能重算」的原则一致。

> 同一家族还有 `weflow-server`（微信 4.x，`:5033`，纯 Rust，同一套接口契约）。我们目前用自持的 `wxread`（已实测能读真实群消息），但**若 `wxread` 将来维护不动，可以平移到 `weflow-server`**——因为适配器只依赖「归一化后的 11 个字段」，不依赖来源。

### 9.4 归一化

复用 `refs/chatlog/80-field-mapping.md` §2.3 的 11 个必需字段。三个平台的差异全部收在适配器里，`chat_msg` 表只存归一化后的形态 + `raw` 原件。

`decisions.md` D6 已经预留了 `channel` 与 `account` 两列——这是上一轮为 QQ 做的**唯一**结构让步，现在正好用上。

### 9.5 两个实现都做，两周后看效果

你说「不是核心部件，可两个都做到时候看效果」——同意，因为**共用归一化层**，第二个实现只多约 150 行。

| | 实现 | 依赖 | 延迟 | 一次性成本 | 主要风险 |
|---|---|---|---|---|---|
| **Q1** | `qqflow-server`（本地 HTTP+SSE） | Rust 二进制 | 近实时（文件事件 + 轮询） | 取一次 16 字节密钥 | 第三方、QQ 升级可能失效 |
| **Q2** | `QQFlow` 桌面版导出（TXT/CSV） | GUI，手动跑 | 分钟级 / 手动 | 无 | 没实时性，接口是文件不是 API |

```
adapters/chatlog/qq/
├─ normalize.py     # 共用：→ 11 个字段
├─ q1_server.py     # 走 HTTP+SSE
└─ q2_export.py     # 走导出文件（watch 目录 + 增量读）
```

配置开关 `chatlog.qq.source = q1 | q2`，两个可同时开（Q2 当兜底：Q1 挂了仍能从导出文件补齐）。

**两周记分卡**（都跑起来之后再评，不预设立场）：

| 指标 | 权重 | 怎么测 |
|---|---|---|
| 覆盖率（群 + 私聊是否都读得到） | 高 | 抽样对比 QQ 里能看到的消息 |
| 延迟（发出到进我们的库） | 中 | 记录 p50 / p95 |
| 是否需要关 QQ / 重启 | 高 | 是否影响你正常用 QQ |
| 密钥失效频率 | 高 | QQ 小版本升级后是否还能读 |
| 杀软 / 系统干扰 | 中 | 是否有告警、是否被拦 |
| 崩溃后能否自恢复 | 中 | 手动 kill 再拉起 |

判据很简单：**覆盖率不到 95% 或需要经常关 QQ 的那个，淘汰。**

## 10. 画像

你已经提到"给朋友侧写画像"。这条要单独设限，否则很容易做成"未经同意的人肉"。

规则：

1. **默认关闭**。只有 `watch.profile_enabled=1` 的会话/个人才生成。
2. **只写可观察行为**：说话频率、常用表达、在群里承担的角色（组织者/提问者/潜水）、公开提到过的偏好。
3. **不写推测**：心理状态、健康、性取向、政治倾向、经济状况——一律不写，哪怕模型"很有把握"。
4. **可删除**：`mephisto profile purge <name>` 一条命令清干净。
5. **画像不投递**。它是给 Agent 用的检索材料，不是给人看的报告。

## 11. 上线的第一周要测什么

| 要测的 | 怎么测 | 决定什么 |
|---|---|---|
| 防抖参数是否合适 | 记录每次 flush 的 `count` 与静默时长分布 | 120s / 20min 要不要调 |
| 接龙识别准确率 | 人工标 20 个接龙，跑检测器 | 正则要不要加规则 |
| 摘要质量 | 抽 10 条摘要人工核对"漏了什么" | prompt 要不要改 |
| 单会话 token 成本 | 记录每封摘要的 in/out token | 是否要换更小的模型 |
| QQ 密钥提取是否稳定 | 按 §9.2 走一次，看杀软是否报警 | 决定 QQ 采集能不能长期自动化 |

## 12. 待定
