# 30 · 工作区与记忆

> 你的方案是：主工作区共享、所有会话有完全权限、每个会话在主文件夹下开子文件夹。
> 这个结构是对的。本文补三件它没覆盖的事：**全权限的代价怎么兜**、**记忆怎么写才不会烂成一堆笔记**、**上下文每次运行拼什么**。

---

## 1. 先给三个概念分家

中文里"心智/记忆"容易被当成一件事。它们其实是三个，混在一起就都做不好：

| 概念 | 是什么 | 存在哪 | 谁能改 |
|---|---|---|---|
| **人格（persona）** | Agent 的语气、价值观、行为边界 | `AGENTS.md` + `persona/` | **只有用户** |
| **世界模型** | 关于项目、人、事实的客观认知 | `memory/{facts,people,projects}/` | Agent 可写，受规则约束 |
| **会话叙事** | 这条会话发生过什么、待办是什么 | `sessions/<sid>/session.md` | Agent 追加 |

**人格必须只读**，否则跑上三个月，Agent 会把自己的临时判断写成"我的原则"，然后开始漂移。这是长期运行的系统里最常见的腐化方式，而且用户几乎察觉不到。

至于"拟人不是必须"——同意，而且建议**主动放弃拟人**。稳定的助手比像人的助手有用：用户需要的是"我知道它会怎么答"，不是"它像个人"。

## 2. 全权限的真实代价

"所有会话对工作区有完全权限"是合理的（个人系统，防不了也没必要防）。但它有两个具体后果，必须设计兜住：

| 后果 | 机制 | 兜法 |
|---|---|---|
| 一条被提示注入的外部内容（群里某人的消息、网页）可能诱导 Agent 删/改共享文件 | 共享工作区 + 完全权限 + 外部内容进上下文 | ①**只追加**为主：`memory/` 与 `journal/` 只允许 append 与新增文件，删除/重写走 `--force` 且要人确认；②**git 每小时自动快照**，坏了 `git checkout` 回来 |
| 多个会话并发写同一个文件 | 并行运行 | ①同一会话串行；②跨会话写 `memory/` 用文件锁 + 短事务；③**不同会话只写自己的 `sessions/<sid>/`**，写 `shared/` 与 `memory/` 要显式声明 |

**"只追加 + git 快照"这两条加起来，就等于给全权限装了一个时间机器。** 代价是每小时一次 commit，几乎为零。

具体到 git：

```gitignore
state/
outbox/sent/ outbox/failed/
sessions/*/transcript/
```

`.git` 里只放 `AGENTS.md`、`MEMORY.md`、`memory/`、`sessions/*/session.md`、`sessions/*/notes/`、`shared/`。这些都是文本，diff 可读——**这也是"记忆可审计"的实现方式**。

> 不要 commit `state/mephisto.sqlite3`：二进制，天天全量 diff，仓库会爆炸。

### 2.1 现状：写边界切在"任务"这一级，太窄

现行实现（`E:\mephisto\mailbot`）把 agent 的写边界设成**当前任务目录**：

```
state/threads/<threadId>/          ← 线程工作区
    └─ jobs/<taskId>/              ← agent 的写边界（workspace-write）
        ├─ inbox/  outbox/  notes/
```

这是对的（最小权限），但它让三件事做不到：

| 想做的事 | 卡在哪 |
|---|---|
| 给这条会话写长期记忆（`context.md`） | 在上一级，**写边界之外**。`AGENTS.md` 里只能写"写不了就算了，放进附件让用户决定" |
| 让会话 A 复用会话 B 的产物 | 跨线程，读不到 |
| 维护全局 `MEMORY.md` | 全局，更读不到 |

`AGENTS.md` 第 112 行那句"**注意它可能在你的写边界之外；写不了就算了**"就是这个结构缺陷的自白。

**修法不是"放开全盘"，是把边界从"任务"上移到"工作区"，再用软约束管住共享区：**

```
workspace/                      ← 写边界（workspace-write）
├─ sessions/<sid>/              ← 会话自己的地盘，随便写
├─ shared/                      ← 共享产物，写要留痕
├─ memory/                      ← 只追加 + 每夜 git 快照
└─ outbox/                      ← 唯一出口
```

三级权限，不是一刀切：

| 区域 | 策略 | 兜底 |
|---|---|---|
| `sessions/<sid>/` | 自由读写（只限本会话目录） | git |
| `shared/`、`memory/` | 写允许，但**只能追加/新建**；删除与覆盖要 `--force` | git 每小时快照 |
| `outbox/` | 只能写，不能读别人未发的 | 发送器校验 |

> 一句话：**把"完全权限"给到工作区，把"不可逆"挡在工具层。** 这比"什么都不能写"和"什么都能写"都好。



## 3. 目录与职责

```
workspace/
├─ AGENTS.md                 # 宪法。≤300 行。身份/边界/工具/写作规范
├─ persona/
│  ├─ voice.md               # 语气与风格（只读）
│  └─ refusals.md            # 明确的拒绝清单（只读）
├─ MEMORY.md                 # 索引，≤200 行。每行：- [标题](路径) — 一句话
├─ memory/
│  ├─ facts/<slug>.md        # 稳定事实：账号、地址、偏好、口径
│  ├─ people/<slug>.md       # 人：角色、关系、可观察的偏好
│  ├─ projects/<slug>.md     # 项目：目标、状态、关键决定、坑
│  ├─ journal/2026-10.md     # 追加流水，只 append
│  └─ inbox/                 # 候选记忆（Agent 只能说"这条值得记"）
├─ sessions/<sid>/
│  ├─ session.md             # 叙事 + 待办（见 §4）
│  ├─ notes/                 # 本会话的过程笔记（草稿，可不进 git）
│  ├─ artifacts/             # 产物
│  └─ transcript/            # 信封副本（可重建，不进 git）
├─ shared/                   # 跨会话复用的产出
└─ state/                    # DB、附件、日志（不进 git）
```

**命名规则**：文件与目录一律小写 ASCII、用 `-` 连接、无空格。中文标题放在文件内容里，不放在文件名里。理由：跨平台迁移、shell 引用、URL 编码——踩过一次就知道。

## 4. `session.md` 的格式

不要写成一坨聊天记录。用固定骨架，Agent 每次只改它该改的部分：

```markdown
---
id: 01JABCD...
slug: s-3f9a1c
title: 报销流程
type: project
created: 2026-10-20
last_active: 2026-10-26
open_items: 2
---

## 目标
把这学期三次出差的报销走完，拿到打款。

## 当前状态
9 月那张单子卡在财务确认，10 月的还没提交。

## 关键事实
- 财务对接人：李（`people/li.md`）
- 报销单模板在 `shared/报销模板.xlsx`
- 发票必须当月开，逾期要写说明

## 待办
- [ ] 等财务确认 9 月单（2026-10-24 起）
- [ ] 提交 10 月单（截止 11-05）

## 时间线
- 10-20 建立会话，整理三次出差
- 10-24 提交 9 月单，财务说"这周给答复"
- 10-26 用户问进度 → 回复"还在等"
```

四个要点：

1. **`前情` 由人写、`时间线` 由 Agent 追加**。前者稳定，后者高频，不要混。
2. **待办是勾选列表**，Agent 每次运行先读它，结束时更新它。这是"会话有连续性"的最低成本实现。
3. **关键事实里只放指针**（`people/li.md`），不复制内容。复制就会不同步。
4. **超过 200 行就压缩**：把「时间线」里超过 14 天的条目压成一句"10 月中旬：提交 9 月单，等确认"，原文进 `notes/archive-YYYYMM.md`。

## 5. 每次运行拼什么（上下文预算）

一次 Agent 调用的固定开销必须可控，否则长会话一定崩。目标：**在开始干活前 ≤ 8k tokens**。

| 顺序 | 内容 | 预算 | 说明 |
|---|---|---|---|
| 1 | `AGENTS.md` | ≤1.5k | 可缓存；改一次影响全局，要克制 |
| 2 | `persona/voice.md` | ≤300 | 短 |
| 3 | `MEMORY.md` 索引 | ≤800 | 只有索引，不是全部记忆 |
| 4 | `memory/projects/<本会话项目>.md` | ≤1.5k | 若会话绑定项目 |
| 5 | `session.md`（前 40 行 + 时间线末 10 条） | ≤2k | **不是全文** |
| 6 | 按本封信检索到的记忆片段（≤5 条，每条 ≤200 字） | ≤1k | grep 命中，见 §9 |
| 7 | 本封信封 + 附件清单 | 余量 | |
| 8 | 可用工具清单 | ≤500 | 由 harness 提供 |

**超过预算时的降级顺序**：先砍 6，再砍 5 的时间线，再砍 3（只留标题）。**永远不砍 1。**

这条降级顺序要写进 `AGENTS.md` 之外的代码里，不能靠模型自觉。

## 6. 记忆分层

| 层 | 内容 | 寿命 | 写谁 |
|---|---|---|---|
| L0 工作记忆 | 当前任务的中间文件（`sessions/<sid>/notes/`） | 一次任务 | Agent 随意写 |
| L1 会话叙事 | `session.md` | 会话 | Agent 追加 |
| L2 长期记忆 | `memory/facts|people|projects` | 长期 | Agent 提议 + 规则校验 + 定期整理 |
| L3 归档 | git 历史 + `notes/archive-*` | 永久 | 整理任务 |

**L2 是最容易烂的一层**。烂的方式很固定：同一条事实被写了五遍、每次措辞略不同；旧事实被新事实覆盖但没有标记；大量一次性的东西被当成"长期记忆"。

三个防烂规则：

1. **一主题一文件，slug 唯一**。写之前先 `grep -l` 找同名文件；找到就**追加到"修订"小节**，不是新建。
2. **每条记忆带来源**。格式固定：
   ```markdown
   - 报销要当月开票（来源：2026-10-24 会话 s-3f9a1c；置信：高）
   ```
   没有来源的记忆，整理时优先删。
3. **冲突不覆盖，并列 + 标日期**。
   ```markdown
   - 财务对接人：李（2026-10 起）
   - 财务对接人：王（2026-08 前）〔已失效〕
   ```
   覆盖式更新会让 Agent 在"到底是谁"上永远摇摆。

## 7. 什么时候写记忆

不要每轮都写，也不要只在会话结束时写——前者噪声大，后者会丢（会话可能永远不"结束"）。用**三段式**：

| 时机 | 写什么 | 谁触发 |
|---|---|---|
| 会话内 | 只写 `session.md`（叙事 + 待办） | 每次运行结束 |
| 会话内，遇到"稳定事实" | 往 `memory/inbox/` 丢一行候选 | 由规则判定（见下） |
| 每晚 | 整理任务把 `inbox/` 归并进 L2，压缩 `journal`，清理过期 | 定时 |

**什么算"稳定事实"**（规则化，不靠模型感觉）：
- 用户明确说"以后都这样""记住"；
- 出现新的实体（人、账号、地址、路径、口径）且在同一会话里被用了 ≥2 次；
- 推翻了旧记忆（必须写）。

其余一律不进。

## 8. 夜间整理任务（具体算法）

```
for f in memory/inbox/*:
    cand = parse(f)
    target = memory/<kind>/<slug>.md
    if not exists(target):
        create(target, cand)                      # 新建
    elif similarity(cand.text, 已有条目) > 0.85:
        drop(cand)                                # 重复，丢弃
    elif 与已有条目矛盾 且 cand 更新:
        append(target, "## 修订 " + date)          # 并列不覆盖
        mark_old_as_superseded()
    else:
        append(target, cand)
archive(memory/inbox/*)

for s in sessions where last_active > 90d and type=project:
    compress(session.md)                          # §4 的压缩规则
    if 已无 open_items: set state=archived

rebuild(MEMORY.md)                                # 重算索引
git commit -m "memory: nightly $(date)"
```

整理任务**不调大模型**（除"相似度"可用便宜模型），全部规则化。理由是它每天跑，成本必须接近零；而且规则化才可审计。

## 9. 检索：先用 grep，别急着上向量

上一轮会话已经测过：8.9 万行中文 `LIKE` 全表 **32 ms**，而 FTS5 的 `trigram` 匹配不了 2 字中文，`unicode61` 把整段无空格中文当一个 token（`refs/wxread/decisions.md` D4）。

推理：如果 8.9 万条消息都能 32 ms 扫完，那么 **几千条记忆的 grep 是微秒级**。向量的收益在这个量级是零，成本是：额外的嵌入调用、索引不同步、中文分词、还要解释"为什么这条被召回"。

**所以 v1：`grep -i` + 一张同义词/别名字典**（`memory/aliases.yaml`，把"报销/报账/费用"指到同一个 slug）。等记忆条目过万、或召回失败率被真实统计出来之后，再上向量。

这条和 `decisions.md` 的 D4 是同一个判断，别在没数据时重开。

## 10. 人格：写什么、不写什么

建议 `AGENTS.md` 里固定这几节，且**全部是可判定的**：

```markdown
## 我是谁
Mephisto，<用户>的个人助手。不是客服，不表演热情。

## 说话
- 先给结论，再给理由。不复述问题。
- 不确定就说不确定，并给出验证方式。不猜。
- 不用"当然可以""很好的问题"这类填充。
- 中文为主；技术名词保留英文原文。

## 边界
- 不代替用户对外发消息（聊天、邮件）——除用户明确指定。
- 不删除 memory/、shared/ 里的既有内容，只能追加与标记失效。
- 不把私人内容写进 pub 会话的上下文。
- 涉及钱、账号、他人隐私的操作，先问。

## 失败时
- 工具报错：原样贴出错误，说明尝试过什么，给下一步选项。不掩盖。
```

注意最后一条：**"工具报错要原样贴出"**。这一条能省掉大量"Agent 假装成功"的麻烦。

## 11. 记忆的隐私边界

- `memory/people/` 里写的必须是**可观察行为与公开信息**，不写推断的心理状态、健康、性取向、政治倾向这类。
- 群聊摘要里出现的人，默认只写"在群里说过什么"，不建画像；建画像要对具体人**显式开启**（`watch.profile_enabled`）。
- `pub` 会话明确不加载 `memory/` 与 `people/`。
- `state/` 与 `memory/` 都不进任何同步盘。

## 12. 四条补强（来自 2026-10 的一手调研）

`research/memory.md` 里逐条核对了 Letta / mem0 / Zep / Anthropic 的公开文档与论文。结论是**上面这套设计主体成立**（文件 + 索引 + grep + 只追加 + 人格只读），但有四条必须补：

### 12.1 索引超限要**硬失败**，不能静默截断

`MEMORY.md` 定 200 行 / 25KB 上限。写入超限时**报错并要求重写索引**，绝不允许"加载时只读前 200 行"。

理由：静默丢尾部意味着 Agent 某天开始"忘记"后写入的记忆，而且没有任何信号。Claude Code 的 `CLAUDE.md` 就是这么做的（超限报错而非截断）。

### 12.2 加一条 `mephisto memory check`（记忆体检）

规则化检查，不调模型：

| 检查 | 判定 |
|---|---|
| 重复 | 两条记忆的规范化文本相似度 >0.85 |
| 死链 | 指向不存在文件的 `[标题](path)` |
| 可推导 | 能从 `projects/` 里直接算出来的东西（如"还有 2 个待办"） |
| 常驻开销 | `MEMORY.md` + `AGENTS.md` 的 token 数超过预算 |
| 互相矛盾 | 同一 slug 下两条未标失效、措辞相反的断言 |

Claude Code 与 Letta 都有等价功能。**没有它，记忆系统三个月后一定烂，而且是悄悄烂。**

### 12.3 每条事实带机器可读的 `modified`，常驻层只渲染 current

```markdown
- 财务对接人：李（modified: 2026-10-24；来源：s-3f9a1c）
- 财务对接人：王（modified: 2026-08-02；superseded: 2026-10-24）
```

好处：生成 `MEMORY.md` 索引时可以只保留 current 那一条，历史仍可 grep 到。**这是"只追加不覆盖"与"上下文要短"这两个要求的唯一共存方式。**

### 12.4 先建评估集，再谈升级检索

20–50 条自有问答（按 LongMemEval 的五类能力：单跳、多跳、时序、更新、**拒答**），在换检索方案前先跑一遍。没有基线数字，任何"升级到向量/图"的讨论都是凭感觉。

"拒答"这一类尤其重要：**记忆系统最危险的失败不是想不起来，是自信地编了一条。**

## 13. 明确不做的事

调研里这几样都查过，结论是**在单用户文件场景下是负收益**：

| 不做 | 为什么 |
|---|---|
| 图数据库 / 时序知识图谱（Zep 路线） | Zep 自己的 DMR 表显示：朴素全上下文 98.0% vs Zep 98.2%，只差 0.2 点；它的真实卖点是同精度下 token 从 11.5 万降到 1.6 千——而我们用文件索引 + grep 已经拿到了这个收益 |
| 四时间戳（valid/invalid × 事件/摄入） | 两个（`modified` + `superseded`）已经覆盖单用户场景 |
| 每轮 LLM 抽取记忆 | mem0 自己在 2026-04 反转成 ADD-only，理由正是"覆盖式更新会丢信息"；每轮抽取则被噪声反噬 |
| 自动衰减曲线 / A-MEM 式记忆演化 | 无法解释"为什么这条被降权"，出问题无法排查 |
| 社区摘要层 | 单用户没有"社区" |

## 14. 待定

- `AGENTS.md` 1.5k token 够不够放下工具约定，要写完才能定。
- 相似度阈值 0.85 是拍的，需要用真实 `inbox/` 数据校准。
- 90 天归档对"半年才用一次"的项目太激进，可能要按 `type` 区分。
- 中文分词：暂不引 `jieba`（`refs/wxread/decisions.md` D4 已否掉 trigram 方案）。等条目过万、且召回失败率被真实统计出来再谈。
