# 20 · 会话路由：怎么决定一封信属于哪条会话

> 这是整套设计里**唯一一个"体验容易崩"的地方**。本文的结论是：**不要靠分类器做主路径**。
> 先把「零输入即可确定」的键用完，分类器只做兜底，且兜底要落到**代价最小的那个错误上**。

---

## 1. 先承认三种错误的代价不对称

用户发一封信，路由有两种错法。它们的代价差一个数量级：

| 错误 | 后果 | 可修吗 |
|---|---|---|
| **误并入已有会话**（A 应该是新话题，被塞进 B） | B 的上下文被污染，后续几轮都在错误的记忆上推理；B 的历史越长，污染越深 | 难。只能事后 `session move`，但 B 里已经被写坏的 `session.md` 回不去 |
| **误建新会话**（A 本该并入 B） | 上下文断裂，Agent 答得浅；用户补一句"接着上次说的"就能救 | 易。`session merge` 一条命令 |
| **误落杂谈**（A 本该进某个项目） | 回答缺少项目背景，但不会污染任何东西 | 易。`session promote` 一条命令 |

**所以兜底必须落到"杂谈"，不是"已有会话"。** 宁可少连一次，不可错连一次。

这条不对称是整个设计的支点。下面的优先级全部由它推导出来。

## 2. 四个键，按可靠性排序

一封回信里，客户端会**自动**带上这些信息（用户不需要做任何事）：

| # | 键 | 谁生成 | 可靠性 | 用户成本 |
|---|---|---|---|---|
| K1 | `In-Reply-To` / `References`（Message-ID 链） | 邮件客户端自动 | **极高**。所有主流客户端都正确回填 | 0（点"回复"） |
| K2 | 收件地址（`To:` / `Delivered-To:`） | 客户端"回复全部"或通讯录 | **极高**。用户只要保存一个联系人 | 0–1 次点击 |
| K3 | 主题文本（剥掉 `Re:`/`回复:` 后） | 客户端自动保留 | 中。用户可能改主题、可能转发 | 0 |
| K4 | 正文语义 | 用户写的 | 低。一封短信没有足够信号 | 0 |

**关键结论：K1 和 K2 已经能覆盖 95% 以上的回信。** 分类器（K4）只处理"全新话题的首封信"——而这恰好是最少发生、也最值得多想一会的场景。

## 3. 路由的优先级链

```
信封进来
  │
  ├─(0) 自环/自动回复过滤：From 是自己、Auto-Submitted、Precedence: bulk → 丢弃
  │
  ├─(1) K0 抽出：从 In-Reply-To / References 里的**我们自己的 Message-ID** 解析会话号
  │        → 该 session，confidence=1.0，不查库、不调模型
  │      （形式见 §5.5：<s7f3a2c.01J...@domain>）
  │
  ├─(2) K1 命中：References 里任一 Message-ID 在 session_alias 里
  │        → 该 session，confidence=1.0，不调模型
  │
  ├─(3) K2 命中：To/Delivered-To 是某个 s-*@ 地址
  │        → 该 session，confidence=1.0，不调模型
  │      （特例：chat@ → 杂谈；pub@ → 公共；m@ → 落到 K3/K4）
  │
  ├─(4) K3 命中：主题里有显式标签（`[T:名称]` 或 `[#slug]`）
  │        → 按标签查/建，confidence=1.0，不调模型
  │
  └─(5) 兜底：分类器
           ├─ 高置信命中已有会话（≥0.80）→ 并入
           ├─ 明确是新话题（≥0.80）且用户显式要新会话 → 新建
           └─ 其余一律 → 杂谈（chatter）
```

**(1)–(4) 全部不消耗 token。** 只有 (5) 调模型，而 (5) 只在"用户主动写了一封没有线程头、没有地址、没有标签的新信"时发生。

## 4. K2：把"会话"做成一个地址

这是解决"打标签太麻烦"的正解：**标签不是一个要输入的东西，而是一个可以选择的东西。**

### 4.1 形态

| 地址 | 语义 |
|---|---|
| `m@<domain>` | 默认入口。按 K1–K4 走 |
| `s-<slug>@<domain>` | **硬绑定**到某个会话。回这封信永远回这条会话 |
| `chat@<domain>` | 杂谈（长驻、低上下文、随便问） |
| `pub@<domain>` | 公共会话（**不读个人记忆**，用于"别把我私人信息带进去"的场合，也是将来对外开放的入口） |

**实现前提**：自有域名 + catch-all，或服务商支持 `user+tag@` 子地址（各家支持情况见 `10-transport-mail.md` §5）。自建域名时 catch-all 是免费的，所以这不是问题。

### 4.2 用户视角

用户**不需要记任何地址**。他做的是：

1. 建会话时，Agent 的回信里有一行页脚：`— Mephisto · 报销流程 (s-3f9a1c)`。
2. 用户把这条会话加进通讯录/或直接对那封邮件「回复」。
3. 以后要说这个话题，从通讯录里选那个地址写新邮件即可。

**这比打标签轻**：打标签要在正文里敲 4–6 个字符并记住语法；选联系人是一次点击，且客户端会补全。

### 4.3 为什么不做成"每个会话一个真实邮箱"

成本与收益不成比例：N 个邮箱要 N 套凭据、N 份额度、N 个 TLS 连接，而 catch-all 只是同一邮箱的 N 个别名，MX 只有一处。**一个信箱 + 多个别名**是唯一合理的形态。

## 5. K1：References 链是主路径

### 5.1 我们怎么发

出站时**必须**带：

```
Message-ID:      <s7f3a2c.01JABCD...@mephisto.example.com>   （会话号写进 ID，见 §5.5）
In-Reply-To:     <来信的 Message-ID>                          （首封信则为空）
References:      <祖→父的全部 Message-ID 空格分隔> <父的 Message-ID>
Subject:         Re: <原主题>                                 （只加一次 Re:，见 §5.3）
```

`References` 的语义是"从根到父的完整链"，不是只有上一封。很多实现只填上一封也能工作（因为客户端会自己补齐），但**自己发的时候必须填全**，否则某些客户端（尤其是 Outlook 网页版）会把同一会话拆成两串。

### 5.2 我们怎么存

`session_alias(kind='message_id', key='<xxx@domain>', session_id=...)`。每发一封、每收一封都往这张表插一行。查一次是主键命中，O(1)。

**这是唯一需要"记住"的东西**：只要这张表还在，线程就永远连得上。它不依赖邮件服务器，不依赖客户端，不依赖 harness。

### 5.3 主题不要乱动

- 只用一次 `Re: `，且要识别已有的 `Re:`/`RE:`/`回复:`/`Re：`（全角冒号很常见），不叠加。
- **不在主题里塞机器标记**（如 `[m:abc]`）。理由：一是用户看得见，二是 Gmail 恰好按主题聚合，改主题反而可能拆串。
- 加前缀也不要，`[Mephisto]` 这种会让长线程的主题变成 `Re: Re: [..]`。

### 5.4 我们怎么容错

客户端损坏线程的情况真实存在（转发、某些网页版、移动端切换）。降级链：

| 断点 | 现象 | 兜底 |
|---|---|---|
| References 被清空 | 主题仍是 `Re: 原主题` | K3：把剥掉前缀的主题与最近 30 天会话标题做模糊匹配（阈值 0.72） |
| 主题被改 | 只剩正文 | K4：分类器 |
| 两者都没有 | 全新信 | 杂谈 + 页脚提示"如需并入某会话，回信加 `[#slug]`" |

### 5.5 为什么把会话号写进 Message-ID

这是一个几乎零成本、但把整个路由从"有状态"变成"可自证"的技巧，来自 Delta Chat：它的群消息 Message-ID 必须是 `Gr.<group-id>.<unique>@domain`。

我们的格式：

```
Message-ID: <s7f3a2c.01J8ZK3M4Q@mephisto.example.com>
              └─会话号─┘ └──唯一后缀──┘
```

收信时，从 `In-Reply-To` / `References` 里正则捞出 `s([0-9a-z]{6})\.` 就能直接得到会话号。

**它解决的三个具体问题**：

| 问题 | 没有它 | 有它 |
|---|---|---|
| `session_alias` 表丢了/重建了 | 全部历史线程断掉 | 从 References 里全部捞回来 |
| 用户用网页版回信、主题被改 | 落到杂谈 | 照样命中 |
| 换机器、换数据库、迁移 | 线程归零 | 历史线程继续有效（只要邮件还在） |

**它是无状态的自证，不是新的状态。** 所以它能和 `session_alias` 并存：表是快路径，ID 里的号是兜底。

注意三条约束：

1. 会话号只能用 `[0-9a-z]`，不要用中文或大写（大小写在某些网关会被改写）。
2. 后缀必须唯一且永不复用（用 ULID 或 UUIDv4 的前若干位）。
3. **不要**把这一串暴露成用户要输入的东西——它只在头里，用户永远看不见。

### 5.6 地址里带一个短的 HMAC

`Reply-To: s-7f3a2c.9c1e@domain`（后 4 位是 `HMAC(secret, session_id)` 的截断）。

作用不是加密，是**防猜**：地址是外发的，一旦泄漏，别人可以往里发信。带 HMAC 后，伪造的会话地址在路由阶段就被拒，不用等到鉴权那一步。

代价：几乎为零（一个 `hmac.compare_digest`）。收益：把"垃圾邮件/探测"挡在模型调用之前。

## 6. K4：分类器怎么写才不像玩具

### 6.1 输入（严格控制在上限内）

```json
{
  "from": "user@example.com",
  "subject": "报销流程走到哪了",
  "body_excerpt": "…前 1500 字…",
  "now": "2026-10-26T09:12:00+08:00",
  "candidates": [
    {"id":"01J...","slug":"s-3f9a1c","title":"报销流程","summary":"9 月报销单已提交…",
     "last_active":"2026-10-24","open_items":["等财务确认"]}
  ]
}
```

`candidates` **由规则先筛到 ≤12 条**（近 30 天活跃 + 关键词重叠 + 同发件人偏好），不把全部会话塞给模型。

### 6.2 输出（必须是闭合枚举）

```json
{"decision":"existing|new|chatter","session_id":null,"confidence":0.0,
 "evidence":"正文里哪句话支撑这个判断","suggested_title":"仅 new 时给"}
```

- `evidence` 必填且必须引用原文片段 —— 这是防幻觉最有效的一招，没有证据就只能是低置信。
- `confidence` 分段使用，不做连续值回归：`<0.5` 丢弃、`0.5–0.8` 降级杂谈、`≥0.8` 才允许执行 existing/new。

### 6.3 策略表（把不对称写进代码）

| 条件 | 动作 |
|---|---|
| `decision=existing` 且 `conf≥0.8` 且候选近 30 天活跃 | 并入 |
| `decision=existing` 但候选已归档 | 并入但先把 `session.md` 摘要注入上下文 |
| `decision=new` 且 `conf≥0.8` 且用户显式说"新会话/新项目/另一件事" | 新建 |
| `decision=new` 且 `conf<0.8` | **杂谈** |
| `decision=chatter` | 杂谈 |
| 解析失败/超时/模型报错 | **杂谈**（永不因路由失败而丢信） |

### 6.4 让它可复盘

每次决策写 `route_decision`：原文、候选集、模型输出、最终动作、用户后续是否手动纠正（`session move` 会回写这条记录）。跑满一个月后，用这张表算混淆矩阵，再决定阈值。

**没有这张表，分类器就永远调不准。**

## 7. 三类会话的准确定义

| 类型 | 上下文 | 记忆 | 生命周期 | 用途 |
|---|---|---|---|---|
| `project` | 全量 `session.md` + 项目记忆 | 可读写 | 长 | 真正的工作会话 |
| `chatter` | 最近 20 条滚动窗口，无项目记忆 | 只读事实、可提议写入 | 永久 | 一次性问题、闲谈、兜底 |
| `public` | 独立空上下文 | **不读个人记忆** | 永久 | 不想泄露私人信息的场合；将来对外开放 |
| `system` | 无 | 无 | 永久 | 摘要投递、提醒、告警（不参与对话） |

`system` 这个类型容易被忽略但它必须有：**摘要和提醒不该占用任何项目会话的上下文**，否则"早上收到一条提醒"就会污染项目状态。

## 8. 修错的路

误路由是常态，修复必须廉价：

| 命令 | 语义 | 实现 |
|---|---|---|
| `session move <msg_id> <sid>` | 把一封信挪到另一条会话 | 改 `session_alias` 的 `session_id`，把正文追加到目标 `session.md` |
| `session merge <src> <dst>` | 合并两条会话 | 重指向全部别名、拼接 `session.md`、留一条 `merged_from` 记录 |
| `session promote <chatter>` | 杂谈升级为项目会话 | 改 `type`，从杂谈窗口生成初始 `session.md` |
| `session rename <sid> <title>` | 改名 | 只改显示名与 slug 无关（slug 不变，避免地址失效） |

**slug 一旦分配就永不变**。地址是外部引用，改了就等于断链。

## 9. 关于"标签"这件事的正面回答

你的直觉是对的：**要求用户在正文里敲标签，一定用不起来。** 但它不是因为"标签没用"，而是因为**输入成本落在了错误的位置**。

三种不增加输入成本的替代：

1. **地址即标签**（§4）。标签是"选谁"，不是"写什么"。
2. **客户端规则**（server-side filter）。Gmail/Outlook 的过滤规则可以把某个发件人/关键词的邮件自动转发到 `s-*@` 地址 —— 一次配置，永久生效，用户零输入。这才是真正的"定制软件置入标签"的邮件版。
3. **自动打标**。标签由 Agent 从内容推断并写库（`session.tag`），只用于检索与展示，不参与路由。用户永远不必知道它存在。

第 2 条是最被低估的：**邮件客户端本身就是一个规则引擎**，而且规则可以改主题/加标签/转发。把"分类"下沉到客户端，比在 Agent 侧做语义分类可靠得多。

### 9.1 现有实现的 `[T:名称]` 要不要删

**不删，降级为 K3。** 它有三个不可替代的用途：

1. **从通讯录新建时**是唯一能指定会话的手段（此时还没有 References）；
2. **修错**：用户发现落错会话，改主题重发即可；
3. **脚本/外部触发**：用 `procmail`/客户端规则批量投递时，标签是最好写的键。

但要明确它**不是主路径**：主路径是 K0（ID 自带）与 K2（Reply-To 地址），用户正常情况下永远不用敲标签。

### 9.2 三条替代新加的（按优先级）

| 手段 | 用户成本 | 可靠性 |
|---|---|---|
| 直接回复（K0/K1） | 0 | 最高 |
| 从通讯录选会话地址（K2） | 1 次点击 | 高 |
| 主题标签 `[T:名称]`（K3） | 敲 6–10 字符 | 高，但用户会烦 |
| 客户端过滤规则 → 自动加标签/转发 | 一次性配置 | 高 |
| 分类器（K5） | 0 | 中，默认落杂谈 |

**"定制软件置入标签"这个想法是对的**——但在定制 App 出现之前，邮件客户端自带的过滤规则就是那个软件。

## 10. 失败模式

| 场景 | 会不会错 | 后果 | 兜底 |
|---|---|---|---|
| 用户直接回复 | 不会 | — | K1 |
| 用户"回复全部" | 不会 | — | K1+K2 |
| 用户从通讯录新建 | 不会 | — | K2 |
| 用户改主题后回复 | 可能 | 落杂谈 | 页脚给 slug |
| 用户转发历史邮件 | 会（转发链不是回信链） | 落新会话 | 分类器 + 人工 merge |
| 同一话题两封信同时到 | 不会 | 串行处理，第二封走 K1 | 队列串行化 |
| 分类器超时 | 不会 | 落杂谈 | 见 §6.3 |
| 攻击者伪造 From | 可能 | 读别人的会话 | 见 `10-transport-mail.md` §10 的发件人白名单 |

## 11. 待定

- 分类器用哪个模型（要便宜、要能返回严格 JSON、要能接受中文主题）。
- 阈值 `0.72 / 0.80` 是拍出来的，必须用 `route_decision` 的真实分布校准。
- `chatter` 窗口 20 条是否够：取决于单条长度，需要实测。
