# 客户端职责与逻辑（交付给 UI 设计）

> 这份文档是给**做界面设计的人**看的：说明这个 App 有哪些状态、每个界面必须承载什么信息、
> 哪些是逻辑硬约束（不能靠视觉绕开），哪些随便你怎么画。
> 配套：`docs/INDEX.md`（代码在哪）、`docs/TEST-PLAN.md`（怎么验）。

---

## 1. 它是什么

Mephisto 的手机端。**不是聊天玩具**：它是坐在你家电脑上的 agent 的唯一入口。

- 你发一句话 → 电脑上的 dsh 真的会执行命令、读写文件、跑脚本
- 回复是**整段**到达的（不是逐 token 流），中间过程只有"阶段 + 秒表 + token 数"
- 没有 Wi-Fi 也能用（走 Cloudflare 隧道到家里那台机器）

**因此界面要回答的三个问题**（设计时始终记着）：
1. 它现在**在干什么**？（排队 / 思考 / 执行到哪一步 / 卡住了）
2. 我这句话**发出去了吗**？（发送中 / 已排队 / 失败可重发）
3. 这是**哪个会话**？（不同会话上下文完全隔离，串了会很糟）

## 2. 三个界面

### 2.1 会话列表

必须承载：

| 信息 | 来源 | 缺失时怎么办 |
|---|---|---|
| 会话标题 | `Session.title` | 无（必有） |
| 最近活动时间 | `Session.lastActiveAt`（ISO，可能为 null） | 不显示，不要猜 |
| 最近一条消息预览 | 客户端缓存 `ChatStore`（**只有打开过的会话才有**） | 降级为「N 轮对话」 |
| 轮数 | `Session.seq` | — |

其他必须有：新建会话入口、连接设置入口（地址 + 令牌）、提醒入口。
**没有**：未读角标（服务端没有未读概念）、搜索（没有接口）、置顶（没有字段）。

### 2.2 对话页

必须承载：

| 信息 | 来源 | 说明 |
|---|---|---|
| 消息气泡 | `messages`（按 `seq` 升序） | `direction=="out"` 是 **agent 的回复**，`in` 是你说的 |
| 时间分隔 | `TimeText`（间隔 ≥10 分钟插一条） | 居中一行小字 |
| 运行状态 | `ProgressTracker.statusLine()` | 形如「执行中 12s · 一步结束 · 6059 tokens / 缓存 5504」 |
| 发件箱条目 | `Outbox`（未终态） | 四种：发送中 / 已排队 / 执行中 / 失败 |
| 失败重发 | 同上，`state==FAILED` | **必须有重发入口**，否则失败静默消失 |
| 打断 | `progress.working()` 时出现 | 杀掉电脑上正在跑的进程树 |
| SSE 连接状态 | `sseStatus` | 「已连接」时可隐藏，异常时要可见 |
| 输入区 | — | 多行（≥3 行自适应），键盘弹出不能遮挡 |

**关键**：一次只允许一个任务在跑。你连着发两条，第二条会**排队**，等第一条结束合并执行。

### 2.3 提醒与权限

必须承载：通知权限、精确闹钟、电池优化三个系统的跳转；常驻开关；待提醒列表（可单条排闹钟）。
这是**最容易出错**的一屏：少开任何一个开关，表现都是"它没提醒我"且**没有任何报错**。

## 3. 状态模型（界面要能表达这些状态）

### 3.1 发件箱（本机，每条消息）

```
SENDING ──202──> QUEUED ──SSE──> RUNNING ──SSE──> DONE
   │                │                │
   └──失败──> FAILED └──取消──> CANCELLED  └──打断──> CANCELLED
```

- `FAILED` 必须给**重发**（复用同一个 `client_msg_id`，服务端幂等，不会变成两条）
- 同一会话排队上限 5 条，超了要提示
- **没有 3 秒后悔期**（已按需求删除）；"反悔"只有：排队中取消、运行中打断

### 3.2 进度

| 状态 | 界面应该给的感觉 |
|---|---|
| `queued` | 在等，不是卡住（显示已排队 + 等待秒数） |
| `running` | 真在跑（秒表在走 + 阶段名 + token 数在变） |
| `done` | 收尾 |
| `failed` | 给原因，不是只转个红点 |
| `cancelled` | 与失败**区分**（是你主动打断的） |

**禁止**用无限循环动画表示"思考中"——它无法区分"在干活"和"死了"。秒表是诚实的。

### 3.3 SSE 连接

`已连接` / `重连中（退避 0.5s→30s）` / `断开`。重连要带 `Last-Event-ID`，界面不需要说这个，但要让用户知道"现在不是实时的"。

## 4. 逻辑边界（这些不是设计能改的）

| 约束 | 原因 |
|---|---|
| 回复整段出现，不能做打字机 | 服务端是提交级事件（`final`），没有逐 token 流 |
| 消息不能编辑后再发同一条 | `client_msg_id` 是幂等键，改了就是新消息 |
| 同一会话不能并行两轮 | 上下文会互相污染，钱也白花 |
| 没有下拉加载更早 | 接口只有 `since_seq` 升序，没有 `before` 分页 |
| 附件上传 UI 暂缺 | 服务端接口已就绪（4 MB/片、≤64 MB），客户端还没接（S9.1） |
| 提醒要响必须配闹钟 | 服务端到点只是写一条 `notice`，手机端得自己 `setAlarmClock` |

## 5. 设计约束（技术侧）

- Jetpack Compose + **Material3**，**不能引入图标库**（没有 `material-icons-extended`）：图标只能用文字符号或自绘简单形状
- 不能引入图片加载库、动画库、自定义字体
- 深浅色都要成立；跟随系统
- 触摸目标 ≥48dp；文本要能容纳中文长句
- `minSdk 29`（Android 10）起

---

## 6. 可以自由设计 / 不可动的部分

**自由**：一切视觉——配色、间距、圆角、层次、动效（除了"假思考"）、列表密度、气泡形状、空状态插画（用形状而非图片）、字体大小与字重选用哪个 M3 token。

**不可动**：
- 三个界面的信息清单（第 2 节表格里的东西不能少）
- 第 3 节的状态必须能被用户区分
- 第 4 节的边界
- 第 5 节的依赖限制

   - 字号用 M3 的哪个 token（`bodyMedium` / `labelSmall` …）
   - 颜色用哪个 role（`surfaceVariant` / `primaryContainer` / `onSurfaceVariant` …）
   - 状态条的位置与高度

## 8. 验收视角（设计稿好不好，用这三条自检）

1. 只看一眼，能否回答"它现在在干什么"？
2. 发送失败时，能否一眼看出"这句没发出去"且知道怎么办？
3. 在深色模式和浅色模式下，信息层次是否都成立？
