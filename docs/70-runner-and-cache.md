# 70 · Runner：DSH 扮演什么角色

> 你插的那句话很关键，而且它把边界划对了：**DSH 不是分发形态，是执行器。**
> 要的只有三样：**现成的工具集**、**对 DeepSeek API 的贴合**、**高缓存命中**。
> 本文把这三件事拆开，说清楚哪些能依赖、哪些一依赖就会被锁死。

---

## 1. 定位

```
Mephisto（产品）          信道 · 会话 · 记忆 · 提醒 · 工作区 · 交付
      │  调用
      ▼
DSH（执行器）             工具 · 上下文管理 · 模型适配 · 缓存友好
      │  调用
      ▼
DeepSeek API
```

**判断标准：如果把 DSH 换成另一个 harness，Mephisto 还剩多少？**

按现在的设计，剩下：收信、路由、会话、记忆、聊天采集、提醒、投递、日志——**全部**。要重写的只有一个 `Runner` 实现。这就是正确的边界。

反过来，如果会话状态存在 DSH 的 session 里、提醒存在 `dsh-schedule` 里、工具状态存在插件里，那么"换掉 DSH"就等于"重做 Mephisto"。**不要那样。**

## 2. 该依赖什么、不该依赖什么

| 依赖 | 理由 | 风险 |
|---|---|---|
| ✅ **工具集**（read/write/edit/grep/glob/pwsh/web/subagent） | 自己实现等于重写一个 Agent，且质量不会更好 | 工具语义随版本变 |
| ✅ **上下文压缩**（compaction） | 长任务的必需品，自己做很难 | 何时触发不可控（见 §4） |
| ✅ **模型适配与重试** | 省掉一堆 API 细节 | 与厂商版本绑定 |
| ✅ **技能（skills）机制** | 把 `chatlog` 之类的 CLI 包成可发现的能力 | 无 |
| ⚠️ **`--session-id` 续接** | 省 token（见 §3） | 会话是机器本地的，且绑 cwd |
| ❌ **会话持久化当账本** | 见 §5 | 换机器/换目录就全丢 |
| ❌ **`dsh-schedule` 当提醒引擎** | 它要求 Host Web Session controller 与 session 持久化才能投递，**headless 装不起来** | 锁死分发形态 |
| ❌ **插件里存业务状态** | 插件是 Node 侧薄壳，状态在人家内存里 | 重启即丢 |

> 那条 ❌ 是最容易踩的：`dsh-schedule` 功能看着正好够用（一次性/每天/每周/cron、按会话投递、重启后恢复），但它的投递**依赖 Web Host 的 Session controller**。用上它，就等于宣布"Mephisto 必须是 DSH Web 常驻"。这与你"不要高度定制的 DSH"直接冲突。
> **所以提醒必须在我们自己的 Python 侧实现**（`50-reminders.md`）。这不是重复造轮子，是保住可迁移性。

## 3. 缓存：机制与三条设计规则

### 3.1 机制（2026 版的准确描述）

数字与出处见 `research/caching-and-devices.md`；这里只放会影响设计决策的部分。

| 事实 | 含义 |
|---|---|
| **全自动**，无 API、不可手动打点；Anthropic 那套 `cache_control` 被**忽略**（不报错也不生效） | 你控制不了"什么时候缓存"，只能控制"字节长什么样" |
| 匹配的是**缓存前缀单元**：必须从第 0 个 token 起一致，且重复长度要完整覆盖一个已落盘单元 | 不是"任意片段命中"，是"从头开始的整段命中" |
| 最小粒度 **64 tokens** | 短前缀不缓存；分歧点最多浪费 63 token，可忽略 |
| `system` → `tools` → `messages` 摊平成一条 token 流，**`tools[]` 也算前缀** | 工具定义顺序/措辞变了，后面全废 |
| TTL：不用就清，**几小时到几天**；官方措辞"尽力而为，不保证" | 不能把缓存当存储 |
| **冷启动有 1–2 次请求的学习期** | 重启后的前 1–2 封必然全 miss，这是正常的，不要去"优化"它 |
| 观测字段 `usage.prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`，且 `hit+miss==prompt_tokens` | 唯一可信的验证手段。很多 harness 读错字段，面板恒 0% |
| 定价（flash 空闲时段，元/百万 token）：命中 **0.02** / 未命中 **1** / 输出 **4** | 1:50 的差距；工作日 9–12、14–18 是高峰段 |

三个直接推论：

1. **越靠前的内容越值钱**。`system` 与 `tools` 在最前面，它们命中，整段就省钱。
2. **动态内容必须往后放**。时间戳、cwd、run id、本封信的内容，只要进了前缀，后面全部失效。
3. **改动是昂贵的**。不是"下一封贵"，是"改一次、之后每次重建都要重新落盘"。

### 3.2 三条硬规则

| 规则 | 做法 | 违反的后果 |
|---|---|---|
| **稳定在前** | `AGENTS.md` → `persona` → 工具契约 → `MEMORY.md` 索引 → 会话摘要 → 本封信 | 命中率掉到接近 0 |
| **字节级稳定** | 同一份文件不做无意义的重排/重新格式化；JSON 序列化固定 key 顺序；不要在开头插"当前时间" | 差一个空格就整段 miss |
| **新鲜度降级** | 时间戳只放在**动态尾部**，且只放到"分钟"粒度 | 每封信的 `now` 都不同 → 尾部天然不命中，可接受；放开头则全废 |

第三条容易被误解：**尾部本来就不会命中，所以时间戳放尾部是对的。** 关键是别让它跑到前面去。

### 3.3 三段式布局

把每一次请求切成三段，**命中率的高低就取决于三段的边界是否稳定**：

| 段 | 内容 | 稳定性 | 占比目标 |
|---|---|---|---|
| **A 冻结段** | `AGENTS.md` + persona + 工具定义 + `MEMORY.md` 索引 | 逐字节不动；改一次要接受一次冷启动 | 50–70% |
| **B 半稳定段** | 工作区状态、会话摘要、检索片段 | 每天变几次 | 20–40% |
| **C 动态段** | 本封信、当前时间、trace id | 每封必变，**永远放最后** | 越小越好 |

两条实现细节：

- **头部做内容 hash 当版本号**。`AGENTS.md` 一变，hash 变，你知道"从这一刻起要冷两次"。
- **工具定义当静态资产**。顺序固定、JSON key 顺序固定、`description` 里不写运行时计数。真实事故：某 harness 重启后重新生成 tools，每次重启付一次 20 万 token 的全 miss。

### 3.4 成本账（用来判断"值不值得优化"）

按 40K 输入 / 1.5K 输出 / 3000 封/月 估算（flash 空闲时段价）：

| 命中率 | 月成本 | 备注 |
|---|---|---|
| 0% | ≈ ¥138 | 冷启动、每次改头部都是这个数 |
| 90% | ≈ ¥32 | 正常水准 |
| 99% | ≈ ¥21.6 | |

**这张表最重要的一行是：90% → 99% 只省 10 元/月。**

所以：

- **主战场是 0% → 90%**（把头部冻结、把动态内容挪到最后、别每次重启都重新生成工具）；
- 到 90% 之后继续抠缓存是浪费精力；
- 高命中率下**输出变成主要成本**（0.006 > 0.0047 元/封），下一步该优化的是**回信长度**（`AGENTS.md` 里那条"≤1200 字"就是在省钱）、`reasoning_effort`、以及**错峰**（空闲时段直接半价）。

这条和我原本的直觉相反，写下来免得以后反复：**省钱的重点不是把命中率从 95 推到 99，是把信封写短、把任务放在便宜时段。**

## 4. 续接 vs 新开

现行实现是 `sessionMode: continue`：同一条任务线复用同一个 DSH 会话（`threads.py` 里存 `dsh_session_id` + `session_workspace` 指纹）。这个判断是对的，但有一个**必须处理的边界**。

### 4.1 续接的收益是真的，但**不是缓存的前提**

先说一个容易搞错的点：**缓存键是（账号, user_id, 模型, 前缀字节），与设备、进程、session id 无关。** 所以：

- "换设备"本身不破坏缓存——破坏缓存的是"重建出不同的字节流"；
- **不固定 `--session-id` 也能吃到缓存**：只要头部字节一致，从第 2–3 封起就会命中公共前缀单元。

固定 session id 的作用是**保证前缀是纯追加的**（append-only），这是最省事的吃满命中的手段；顺带还有两个真实收益：模型看得到前面几封的原话（比摘要准），以及不用每次重拼上下文。

**所以 `sessionMode: continue` 该保留，但理由要改**：它是"质量 + 省事"，不是"没有它就吃不到缓存"。

### 4.2 续接的代价

| 代价 | 说明 |
|---|---|
| **绑机器、绑目录** | DSH 按 cwd 归档会话，`--session-id` 会校验 cwd 与 preset；换机器/换目录必须降级开新会话（现行实现已正确处理，有 `session.degrade`） |
| **历史无界增长** | 到某个点必然触发 compaction |
| **compaction 是一次缓存悬崖** | 压缩会**改写前缀**，下一次请求整段 miss，同时可能丢掉关键细节 |

### 4.3 所以：把 compaction 变成我们主动的"换代会"

不建议让 harness 在任意时刻自动压缩。改成**在自然边界主动换会话**：

```
任务完成 → 写出 session.md（摘要 + 待办）
        → 主动丢弃 dsh_session_id
        → 下一封信开新会话，前缀 = system + 注入的 session.md（小、稳、可控）
```

好处：

- 压缩发生在"任务之间"，不在任务中途，质量损失可控；
- 前缀由我们决定，稳定；
- 代价是每次换代多付一次"重建摘要"的 token——比让压缩发生在关键推理中途便宜得多。

**触发换代的建议阈值**：`runs >= 12` 或 `session.md 摘要 > 1.5k token` 或 `距上次换代 > 7 天`，三者任一。

> 这就是把"缓存友好"与"可迁移"这对矛盾拆开的办法：**日常靠续接吃缓存，边界处主动换代保迁移性。**

## 5. 多设备：能做什么、不能做什么

你的判断是对的，这里给硬证据。

### 5.1 事实：harness 会话是本机文件

`~/.dsh/sessions/<cwd 编码>/<session-id>/session.v4.jsonl.zstd` —— `[确认-实测]`。

- 没有跨机同步机制；
- 会话**绑定 cwd**（`--session-id` 会拒绝另一个工作目录的会话）；
- 两台机器各自跑，会得到两条互不相干的会话。

**结论：不能让手机和电脑"处理同一条会话"。** 这不是配置问题，是模型问题（会话 = 本地文件 + 本地 cwd）。

### 5.2 但你其实不需要

真正需要共享的是**状态**，不是**会话**：

| 东西 | 放哪 | 能不能共享 |
|---|---|---|
| 会话叙事 `session.md` | 工作区文件 | ✅ git / 同步盘 |
| 记忆 `memory/` | 工作区文件 | ✅ |
| 结构化状态（游标、提醒、额度） | SQLite | ⚠️ 单写者，只能在一个节点 |
| harness 会话 | 本机 | ❌ 不需要 |

所以形态是：**一个"家"节点执行，其他设备是纯客户端。** 手机收邮件、发邮件、看附件——今天就能用，零开发。

这正好也是 Delta Chat 的做法：它没有服务器，多设备靠"给自己发一份副本（BccSelf）"让各端看到同一批信。**邮件天然就是同步机制。**

### 5.3 什么时候才需要考虑"手机也执行"

只有一个场景成立：**断网/离线时也要能派活**。那时需要的不是共享 DSH 会话，而是：

1. 手机上有本地模型或 API 直连；
2. 手机的"任务"写进一个可合并的队列（而不是直接改工作区）。

这两件事都不该在第一阶段做。**先做"手机是客户端"，够用很多年。**

## 6. 最大的风险：DSH 升级

DSH 是活跃开发中的项目（`0.2.0-rc.2`）。升级会带来：

| 变化 | 后果 |
|---|---|
| 系统提示/工具定义改写 | 缓存前缀变了 → 冷一次；行为可能轻微漂移 |
| 会话格式升级（v0→v1→…→v4） | 旧会话要迁移；跨版本续接可能失败（现行实现已有降级路径） |
| 工具语义/参数变化 | `AGENTS.md` 里的用法说明要跟着改 |
| profile/patch 语义变化 | `bootstrap.py` 生成的 `cordis.patch.yml` 可能要重写 |

**对策三条**：

1. **钉版本**：记录当前 `dsh` 版本与 profile 结构，升级前先在旁边跑一遍 `tests/run_all.py` 与一次端到端。
2. **降级路径要是常态**：续接失败 → 新会话重跑（已经这么做了），而不是报错。这条要一直保留。
3. **业务状态永不放 harness**：见 §2。

## 7. Runner 接口（逃生舱）

```python
class Runner(Protocol):
    def run(self, *, cwd: Path, task: str, session_id: str | None,
            timeout_s: int) -> RunResult:
        """返回 (final_text, session_id, usage, degraded)"""
```

四个实现，第四个是新的首选：

| 实现 | 用法 | 什么时候用 |
|---|---|---|
| **`sdk`** | `DeepSeekHarness(dsh_home=…, profile=…, patches=(…)).run(task, session_id=…)` | **推荐**。进程常驻、`resume_session` 续接、不依赖系统 Node（见 `65-distribution.md`） |
| `dsh-cli` | `dsh --profile mailbot --session-id <id> "<task>"`（现行） | 迁移期/排障时用它对照 |
| `dsh-json` | 同上 + `--json`，拿 `session` 事件与 usage | 需要统计缓存命中/成本时 |
| `api` | 直接打模型 API，自己跑工具循环 | 逃生舱（DSH 挂了/换厂商） |

**为什么 `sdk` 更好，不只是"少装 Node"**：

- **进程常驻**：SDK 懒启动并复用同一个 runtime 直到 `close()`，而不是每封信 spawn 一次。冷启动从"每封一次"变成"启动一次"。
- **`resume_session(id)` 是一等 API**：它"恢复持久化历史、修复被打断的最后一轮、不发送新输入"，且要求用同一 `dsh_home` 与 workspace——正是我们需要的续接语义。
- **`dsh_home` 必须显式给**（拒绝空值、永不回落 `~/.dsh`）：默认就隔离，不会污染用户的 DSH 安装。
- **`patches=(...)` 可以按次传入**：profile 资产变成"仓库里的文件"，而不是"写进 `$DSH_HOME` 的机器状态"。这一条直接改善了可迁移性。

代价：它选的 profile **必须包含 `@deepseek-ai/dsh-sdk-jsonrpc-server` 行**，所以现在基于 `headless` 的 `mailbot` profile 不能直接复用，要换 `sdk` 模板重建。详见 [`65`](65-distribution.md) §4.1。

**`dsh-json` 仍然值得保留**：`--json` / SDK 的用量回传是**唯一能验证"缓存到底有没有命中"**的手段。没有它，所有关于省钱的判断都是猜。

> 注意 `--json` 的边界：除了终止的 `final` 事件，其它字符串被截到 8 KiB，而且它是**投影不是日志**。所以：用它做统计，不要用它做记录。

## 8. 结论

| 问题 | 答案 |
|---|---|
| DSH 是分发形态吗 | 不是。是执行器 |
| 该依赖它什么 | 工具、压缩、模型适配、技能 |
| 不该依赖什么 | 会话持久化（当账本）、`dsh-schedule`、插件内状态 |
| 缓存怎么吃满 | 头部逐字节冻结、`tools[]` 也算前缀、动态内容永远放最后；**边界处主动换代**。但先做 0%→90%，别抠 90%→99% |
| 手机能一起跑吗 | 不能共享会话；也不需要——手机是客户端，执行只有一个"家"节点 |
| 最大风险 | 升级改前缀/改格式。对策：钉版本 + 降级当常态 + 状态不落 harness |
