## 2. 明文还是密文：判定为密文 `[确认-实测]`

三个库的一致结果：

| 库 | `size % 4096` | `(size-1024) % 4096` | 正文熵 | 可打印率 |
|---|---|---|---|---|
| `nt_msg.db` | 1024 | **0** | **8.00** bits/byte | **37.1%** |
| `group_info.db` | 1024 | **0** | 8.00 | 37.2% |
| `misc.db` | 1024 | **0** | 8.00 | 37.2% |

判据（三条同时成立只能是密文）：
1. 熵 **恰好 8.00**（明文 SQLite 一般 4–6）；
2. 可打印率 **37.1%** = `95/256`，正是**均匀随机字节**的理论值；
3. 在 59 MB 里搜 `SQLite format 3`、`CREATE TABLE`、`sqlite_`、`group_msg`、`c2c_msg` —— **全部 0 命中**。

**尺寸关系**：`size = 1024 + N × 4096`，`N = 14485` 页 → 结构是「**1024 字节前缀 + 标准 4096 页**」。

## 3. 那 1024 字节前缀是什么（本章新结论）`[确认-实测]`

有效内容只有 **201 字节**（offset 0x00–0xC8），其后 823 字节全零。逐段：

```
0000  53 51 4c 69 74 65 20 68 65 61 64 65 72 20 33 00   "SQLite header 3\0"  ← 诱饵魔数
0010  04 00 10 00 00 00 00 00 ...                       04 00 = 页大小 1024  ← 诱饵
0020  51 51 5f 4e 54 20 44 42                           "QQ_NT DB"
002c  12 80 01 <128 字节>                               protobuf f2：128 字节 hex 串
00af  1a 07 "1.1.0.1"                                   protobuf f3：库格式版本
00b8  22 09 "HMAC_SHA1"                                 protobuf f4：页 MAC 算法
00c3  28 b6 e2 b0 d3 06                                 protobuf f5：varint 1,785,475,382
```

**三条解读**：

1. **前 16 字节是诱饵**：`"SQLite header 3\0"` 而不是 `"SQLite format 3\0"`，紧跟一个**假页大小 1024**。这是在**故意骗工具**——真实现是 4096 页。
2. **f4 = `HMAC_SHA1` 写在文件里**：公开文档说的算法，从**文件自身**得到了印证，不必只信文档。
3. **f5 = 1,785,475,382** 换算成本地时间是 **2026-07-30**，与 QQ 安装/建库时间（07-31）吻合 → 极可能是**模板构建时间戳** `[推断]`。
4. f2 那个 128 字节 hex 串语义未知 `[未验证]`；它在 22 个 `.db` 里分 **3 种**（18 个共用一种、3 个一种、1 个一种）→ 像是按库族出现的标识。

> `71-*.md` 当时写「1024 字节头的结构没有任何公开描述」。现在**本机这份有了**：诱饵头 + `QQ_NT DB` + 4 个 protobuf 字段。但**里面没有 `kdf_iter`、没有盐、没有 key**——所以解开头也读不出内容。

## 4. WAL：**没有** 1024 字节前缀，而且真的有待应用帧 `[确认-实测]`

这是全章最有实用价值的一条，也是**微信侧给不了的正例**。

| 文件 | 大小 | 头 | 帧数 | 匹配当前盐代 | 最后 commit |
|---|---|---|---|---|---|
| `nt_msg.db-wal` | 2,216,592 | 标准 WAL 头（`377f0682`, psize 4096） | 538 | **91** | idx 90, pgno 14483, **ntrunc 14485** |
| `group_info.db-wal` | 531,512 | 同上 | 129 | 49 | idx 48, ntrunc 990 |
| `misc.db-wal` | 428,512 | 同上 | 104 | 77 | idx 76, ntrunc 146 |

- **`(size-32) % 4120 == 0`**：WAL 是标准 SQLite WAL 布局，**不带那 1024 字节前缀**。所以「剥前缀」只对主库做，WAL 直接按标准解析。
- `nt_msg.db-wal` 的当前盐代有 **91 帧**，且第 90 帧是 commit，`ntrunc = 14485` 恰好等于主库页数 → 这是一个**完整、待应用的事务**。
- 其余 447 帧属于**更老的盐代**（`10125e77` ×221、`10125e74` ×112…），是预分配文件里的残留。

**交叉意义**：微信侧四个库的 WAL 都是「头比所有帧新 → 0 帧可用」，我无法验证"有帧时能不能正确应用"。**QQ 这份 WAL 正好补上了这个正例**：盐代过滤 + 取到最后 commit 的算法，在这里得到 `91 帧 / commit@90 / ntrunc=主库页数` 的完整验证。
（帧内容能否用同一套页布局解出，仍需 key，`[未验证]`。）

## 5. 取 key：锚点在，钥匙不在手里

**公开方法**（`QQBackup/qq-win-db-key`，读过全量源码，见 `evidence/qq/ntqq-localdb-crypto-key.md`）：
静态找字符串 `nt_sqlite3_key_v2: db=%p zDb=%s` → 找引用它的 `LEA` → 用 `.pdata` 反推函数 RVA → 以 `DEBUG_ONLY_THIS_PROCESS` 启动 QQ → 函数入口下 `0xCC` → 命中后读 **R8 寄存器**（x64 第 3 参 = pKey）。

**本机验证**：该锚点字符串在 `9.9.33-51802` 的 `wrapper.node` 里**存在**（offset 74,246,776）。`sqlite3_key`、`nt_msg.db` 也都存在。
→ 说明**方法对本机这个版本仍然适用**；但"能定位到"不等于"能跑通"，`[推断]`。

**卡点（硬）**：

| 卡点 | 本机状态 |
|---|---|
| 需要管理员权限 | **当前是标准用户** → `DEBUG_ONLY_THIS_PROCESS` 起不来 |
| QQ 必须以被调试方式启动 | QQ 当前未运行，可配合 |
| 公开验证版本止于 **9.9.32-51246** | 本机是 **9.9.33-51802** → 版本适配 `[未验证]` |
| 会 hook 到长度 20 的 key | 那是 `login.db` 的硬编码 key，必须按"16 字节 + 可打印"过滤才不拿错 |

## 6. 三条路的能力与代价（本机视角）

| | 官方 Bot | NapCat | 本地库直读 |
|---|---|---|---|
| 能读**实时**群消息 | ✅（`GROUP_MESSAGE_CREATE` + 群主开「接收全量消息」） | ✅ | ❌（只能轮询文件） |
| 能读**历史** | ❌ **无历史 API** | ✅ | ✅（回溯能力最强） |
| 本机已具备条件 | ❌ 需注册 bot + 公网可达回调 | ❌ 未装（extension 不可枚举，无法确认） | ⚠️ 库在、格式已解、**缺 key 且需提权** |
| 需要扫码/登录 | 否（bot 身份） | ✅ 需账号登录 | 否（但要 QQ 跑一次以抓 key） |
| 稳定性风险 | 平台合规/权限门槛 | **无只读配置**、有不可修的离线缺口（issue #1838，`not_planned`，维护者称 feature） | 版本漂移；调试器可能被检测 |
| 解析工程量 | 小（JSON 事件） | 小（OneBot 11 JSON） | **大**（`40800` 是嵌套 protobuf，含大量未知字段） |

## 7. 结论：对「QQ 这边怎么办」的具体判断

**B5 的答案**：本机 QQ 的消息**现在读不了**。缺的不是知识，是**那个 16 字节口令**；而拿它需要**一次提权 + 以调试方式启动 QQ**。

按"要花的力气 / 能拿到什么"排序：

| 优先级 | 做法 | 能拿到 | 代价 |
|---|---|---|---|
| 1 | **先不做 QQ**，把微信那条链（已通）跑完整 | 微信全量 + 增量 + 摘要 | 零额外风险 |
| 2 | 官方 bot，只做**实时增量** | 今后的群消息（无历史） | 注册 + 公网回调；做不了回溯摘要 |
| 3 | 本地库 + **一次性 hook 取 key** | 全部历史（回溯能力最强） | 提权 + 版本适配 + protobuf 解析 |
| 4 | NapCat | 历史 + 实时 | 需账号登录、无只读、有离线缺口 |

**我的建议**：走 1 → 需要 QQ 再说 2；**3 只有在"必须回溯 QQ 历史"时才值得**，而且要先解决提权这个前提，不是技术问题而是条件问题。

**一个诚实的时间戳**：QQ 库最后一次写入是 **2026-09-16**，此后一个月没登录。所以就算今天解开了，它对"最近一个月的 QQ 消息"也是**空的**——真正的新消息只会在登录后产生。

## 9. 未验证清单（不含糊）

1. `nt_msg.db` 解出的页是否真是 4096 / reserve 36（16 IV + 20 HMAC-SHA1）——**需 key 才能验**。
2. `kdf_iter = 4000` 在本机这版是否仍成立——公开文档的说法，**未在本机复现**。
3. WAL 帧是否用同一套页布局加密——**需 key**。
4. `wrapper.node` 里锚点能否实际定位到函数 RVA（`.pdata` 二分在 9.9.33 上是否成立）——**未跑**。
5. `40800` 里各类消息（图片/语音/文件/引用/合并转发）的字段布局。
6. 那 128 字节 hex（protobuf f2）的语义。
7. `extension` 目录里到底有什么（ACL 拒绝枚举，需提权或改 ACL）。
8. QQ key 是否跨登录/跨版本稳定（决定"抓一次还是每次抓"）。
