## 1. 十条结论速览

1. **WeFlow 有两个形态，差别是本质的。** 仓库 `5.0.0` 把 WCDB/密钥/图片解密全部外包（"第三方可插拔组件"），单靠 clone **跑不起来**；官方 TG 分发版内置 `wcdb_api.dll`(1.65 MB) + `WCDB.dll`(9.22 MB) + `wx_key.dll`(0.23 MB) + 图片解密 addon + `welive.exe`。→ `00-baseline.md`、`41-*.md`

2. **"过期"是"本地倒计时 + 远端可吊销"两层，外加三道辅助闸门。** 主因是组件里**写死截止日期 `2026-10-16 00:00`**，到点即 `-101`（我会错判成"没有到期日"，因为日期以数值常量而非字符串存在，见 `50-*.md` §5 的方法论更正）。辅助闸门： ①`wcdb_runtime_policy_version()` 必须精确等于 **`1464206081`**，否则 `-103`；②每次初始化都要一个 **TTL 180 秒**的本地授权 grant（127.0.0.1 临时端口 + 24 字节随机 token）；③DLL 内部走 `api.weflow.top/api/token` 拿带 `expiresIn` 的令牌 + 离线防回拨（`-102`/`-105`）；④完整性校验。**官方改一次常数，旧版立即全废。** → `50-*.md`

3. **`-101` 的真实含义是"保护状态不成立"，不是"杀毒软件"。** 触发源至少有三种：日期已过、非宿主进程、状态不匹配。真机时间线可自证：2026-10-07 打印 `native protection ok` 并成功读库；2026-10-25 只剩 `native runtime policy mismatch value=-101`。→ `50-*.md` §4.2、`evidence/weflow-policy-probe-*.txt`

4. **真实 ABI 比仓库文档大 21 个函数。** 二进制有 **115** 个按名导出，文档只列 95 个；多出的包括 `wcdb_authenticate`、`wcdb_runtime_policy_version`、`wcdb_set_my_wxid`（文档写作 `set_my_account_id`，名字是错的），以及**一整个 `wcdb_ai_*` 家族（13 个）**——官方把"给 AI 用的上下文/时间线/话题聚合"直接做进了原生层。→ `40-*.md` §2

5. **HTTP API 可以完全绕开 UI，但绕不开 Electron。** 服务启动时自己 `ensureDbReady()`（源码注释明写"未走 GUI 的 connect/warmup"），配 `silentStartup` + 托盘即可无窗口常驻。但 `http.createServer` 在 Electron 主进程里，`WeFlow.exe` 必须活着。→ `30-*.md` §7

6. **推送只有 SSE，没有 webhook。** 事件 `message.new` / `message.revoke`，去重键 `event + rawid`；SSE 带 10 分钟 / 1000 条重放缓冲（`Last-Event-ID`），超时即永久丢失。配置里没有任何 `webhook`/`callback` 键。→ `30-*.md` §4

7. **实时性不是 `fs.watch`，是原生监视管道。** `chatService.ts` 虽然 `import { watch }`，但全文件没有 `watch(` 调用；事件源是 `wcdb_start_monitor_pipe` → 命名管道 → `net.createConnection`，断线 3 秒重连。推送判定靠"会话未读数基线比对"，撤回靠"系统消息 + 文本含撤回 + 未读数下降"三信号，**只回看 150 秒**。→ `10-*.md` §3

8. **`localType` 有复合值，这是最容易踩的解析坑。** `244813135921 = (57<<32)|49`，即"基类型 49 + appmsg 子类型 57"；`8589934592049 = (2000<<32)|49`（转账）。代码自己把前者与 XML 里 `<type>57</type>` 写成等价，可反证这个结构。**判断类型必须先 `& 0xFFFFFFFF`。** → `20-*.md` §3.2

9. **反撤回会改写微信数据库。** `wcdb_install_message_anti_revoke_trigger` 在你的消息库上建 `_weflow_anti_revoke_*` 表和 `AFTER DELETE`/`INSERT` 触发器，把撤回的消息抄下来再插回去。这与任务书 §8.5「不写数据目录」**直接冲突**，只读场景必须排除。→ `20-*.md` §6

10. **QQ 侧三条路线各有致命短板，且短板互不相同。** 官方 Bot：合规、能读全量，但**没有历史接口**；NapCat：能读能推，但**离线期间的消息永久空洞**（维护者称"是 feature"，issue `#1838` 以 `not_planned` 关闭）且**没有只读开关**；NTQQ 本地库直读：能通（`nt_msg.db` / SQLCipher4 / `kdf_iter` 4000 / hook `nt_sqlite3_key_v2` 取 16 字节口令），但**解析层要自己写**（数字列名 + 嵌套 Protobuf）。→ `60/70/71-*.md`

## 5. 怎么用这份报告

- **想最快拿到"能读群消息的服务"** → 读 `30-*.md` §7 与 §8（纯 HTTP 服务 + 调用序列），接受"必须常驻 WeFlow.exe + 会过期"两个约束。
- **想自己实现数据层（长期自持）** → 读 `40-*.md`（115 个导出就是全部接口面）+ `20-*.md`（列与编码）。
- **想评估 QQ 是否可行** → 读 `60-*.md` 的矩阵 + `90-*.md` B 节。当前最优的合规路线是官方 Bot，但**样本不足以下"能稳定读一年"的结论**（缺问题 #11）。
- **想知道"到底会不会过期"** → 读 `50-*.md`。答案：**会，而且已经过期了**（截止日 `2026-10-16`）；另有远端可吊销的常数与在线令牌。
- **想让"读取"本身长期成立（而不是把消息导出）** → 读 `55-*.md`。答案：读取有 4 层，只有 2 层与微信版本耦合；密钥已实测可脱离组件自持（64 hex），SQLCipher 与解码两层一旦自建就永久有效。

## 6. 一次诚实的能力声明

本报告最强的证据是：源码行号、DLL 导出表、asar 解包产物、真机日志与真机目录枚举。
最弱的环节是：**所有"端到端跑通"都缺最后一步**（本机无授权上下文 / 无 QQ 测试号）。

因此：**不要把本文当作"已验证可用"的方案书，它是"地形图"** —— 哪里是坑、坑多深、哪条路要收费，都标了；但过河要你自己试。
